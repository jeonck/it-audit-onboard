# RAG (Retrieval-Augmented Generation, 검색 증강 생성)

RAG(Retrieval-Augmented Generation) 의 가장 본질적이고 핵심적인 아이디어는 바로 이것입니다.

> **"LLM 이 모르는 외부 지식을 실시간으로 검색 (Retrieval) 해서 → 그걸 컨텍스트 (Augmentation) 로 넣어줘서 → 더 정확하고 신뢰할 수 있는 답변 (Generation) 을 만들자"**

이 한 문장이 RAG 의 99% 를 설명한다고 봐도 과언이 아닙니다. 2026 년 현재 거의 모든 자료와 실무에서도 이 관점이 일관되게 강조되고 있어요.

---

## 왜 이게 핵심인가? (LLM 의 근본 약점 해결)

LLM 단독으로는 아래 문제들이 필연적입니다:

- **지식 cutoff** → 2024 년 이후 정보 모름
- **기업/도메인 내부 지식** → 훈련 데이터에 없음
- **환각 (hallucination)** → 모르는 걸 지어냄
- **최신성/정확성 부족** → 파인튜닝 비용 폭발

→ RAG 는 **"모델을 다시 가르치지 않고"** 외부 지식을 동적으로 빌려오는 방식으로 이 모든 문제를 저비용·고효율로 해결합니다.

### 아주 간단한 한 줄 비유 (2026 년 실무에서 가장 많이 쓰이는 표현)

| | |
|---|---|
| **LLM 단독** | 똑똑하지만 기억이 짧은 사람 (훈련된 지식만 앎) |
| **RAG** | 필요할 때마다 책상 위 서랍·구글·내부 위키를 뒤져서 정확한 자료를 꺼내 보여주는 조수를 붙여준 사람 |

결국 **"검색 → 컨텍스트 제공"**이 조수의 핵심 역할이고, 그 덕분에 LLM 이 훨씬 덜 헛소리하고, 최신·정확·근거 있는 답변을 하게 됩니다.

### 2026 년 관점에서 조금 더 세밀하게 보면

- **기본 RAG** → 외부 지식을 검색해서 컨텍스트로 주는 것
- **Advanced/Agentic RAG** → 검색 자체를 LLM 이 여러 번 반복하거나, 그래프·온톨로지·멀티홉으로 더 똑똑하게 함
- **GraphRAG / Knowledge Graph RAG** → 단순 텍스트 검색이 아니라 관계 (relationship) 까지 이해해서 컨텍스트 제공

하지만 모든 변형의 뿌리는 여전히 **"외부 지식 검색 → LLM 컨텍스트 증강"**입니다.

---

## RAG 의 핵심 3 단계 (가장 중요한 흐름)

| 단계 | 이름 (영문) | 핵심 역할 | 2026 년 실무 포인트 | 실패하면 생기는 문제 |
|------|------------|----------|-------------------|---------------------|
| **1** | **Retrieval (검색)** | 사용자 질문 (Query) → 외부 지식 베이스에서 관련 문서/청크 가장 잘 맞는 것 찾기 | 벡터 DB + 임베딩 모델 + 하이브리드/리랭킹이 핵심 | 잘못된 문서 → 완전 엉뚱한 답변 |
| **2** | **Augmentation (증강)** | 검색된 문서 → LLM 프롬프트에 컨텍스트로 끼워넣기 (Prompt Engineering) | 컨텍스트 압축, 순서 최적화, 메타데이터 활용이 성능 좌우 | 컨텍스트 과다 → 토큰 초과 or 혼란 |
| **3** | **Generation (생성)** | 증강된 프롬프트 → LLM 이 최종 답변 생성 | grounding(근거 제시) 강제, citation 자동화가 표준 | 여전히 hallucination 발생 가능 |

→ 이 3 단계가 하나의 루프로 작동 → **"Retrieve → Augment → Generate"**

---

## RAG 가 왜 필요한가? (핵심 문제 해결)

| LLM 단독의 문제점 | RAG 가 해결하는 방식 | 2026 년 실무 효과 (대부분 기업 사례) |
|------------------|---------------------|----------------------------------|
| 훈련 cutoff 이후 정보 모름 | 실시간/최신 외부 데이터 검색 | 최신 정책·뉴스·내부 DB 즉시 반영 |
| 회사·도메인 내부 지식 없음 | Private 데이터 (내부 위키, 매뉴얼, CRM 등) 검색 | 기업 챗봇·내부 지식 에이전트 가능 |
| 환각 (Hallucination) 빈발 | "근거 문서만 보고 답변해" 강제 → 사실 기반 응답 | 환각률 50~80% ↓ (실제 벤치마크 다수) |
| Fine-tuning 비용 폭발 | 모델 재학습 없이 → 벡터 DB 만 업데이트 | 비용 1/10 이하, 업데이트 속도 100 배 빠름 |

## 2026 년 현재 RAG 의 핵심 구성 요소 (실무에서 가장 중요한 것들)

### 1. 임베딩 모델 (Embedding Model)

질문과 문서를 같은 벡터 공간으로 변환

- **2026 년 표준**: OpenAI text-embedding-3-large, Cohere Embed v3, Voyage AI, BGE-M3, Korean fine-tuned 모델 (E5-mistral 등)

### 2. 벡터 데이터베이스 (Vector DB)

- **주요 제품**: Pinecone, Weaviate, Qdrant, Milvus, Chroma, PGVector 등
- **핵심 기능**: 하이브리드 검색 (키워드 + 벡터) + 메타데이터 필터링 필수

### 3. 청킹 (Chunking) & 인덱싱 전략

- 문서를 의미 단위로 자르기 (Semantic chunking, Hierarchical, Sentence-window 등)
- **2026 년 트렌드**: Fixed-size 보다 의미 기반 청킹 + Metadata enrichment 가 성능 크게 좌우

### 4. 리트리버 최적화 (Retriever Enhancement)

- **Query Rewrite / HyDE / Multi-query**
- **Re-ranking**: Cohere Rerank, bge-reranker, RankGPT 등
- **Multi-hop / Agentic Retrieval**: 복잡 질문 → 여러 번 검색

### 5. 생성 단계 강화

- **Grounding 프롬프트**: "주어진 문서만 보고 답변", "출처 명시 필수"
- **Self-Reflection / Corrective RAG**: 답변 후 검증 루프

## 요약: RAG 한 줄 정의 (2026 년 가장 명쾌한 버전)

> **"LLM 이 답변 전에 '모르는 건 검색해서' 알려주고, 그걸 보고 정확하게 말하게 하는 아키텍처"**
>
> **RAG 없이 LLM 쓰는 건** → "기억력 좋은 사람에게 아무 책도 안 주고 질문하는 것"
>
> **RAG 있이** → "필요한 책만 쏙쏙 뽑아서 보여주고 질문하는 것"

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 RAG 시스템 도입 시 고려사항:

1. **검색 품질 검증**: Retrieval 단계의 정확도 (Precision/Recall) 측정 및 모니터링
2. **환각 감소 효과**: RAG 적용 전후 hallucination 발생률 비교 검증
3. **보안·접근제어**: Private 데이터 검색 시 권한 기반 필터링 적절성 검토
4. **성능·비용 분석**: 벡터 DB 운영 비용 vs Fine-tuning 비용 비교 분석
5. **최신성 유지 관리**: 지식 베이스 업데이트 주기와 프로세스 검증
6. **근거 추적성**: 답변의 출처 (citation) 명확성과 검증 가능성 확인
