# AI 서비스 MSA 분해 전략

AI 서비스를 마이크로서비스 (MSA) 로 분해할 때는 일반적인 소프트웨어 공학의 원칙에 **AI 특유의 인프라 및 모델 운영 (MLOps) 특성**을 결합해야 합니다.

특히 엔지니어님께서 언급하신 **비용, 리소스, 레이턴시** 등의 항목은 인프라 효율성을 결정짓는 결정적 요인입니다.

제시해주신 항목들을 기준으로 AI 서비스 분해 전략을 상세히 정리해 드립니다.

---

## 1. 비즈니스 및 조직 기반 분해 (Organizational Context)

시스템의 복잡도를 관리하고 팀 간의 협업 효율을 높이는 **소프트웨어 설계의 근본 기준**입니다.

### 비즈니스 도메인 경계 (Bounded Context)

> 서로 다른 비즈니스 로직 (예: 고객 지원 vs. 내부 분석) 이 섞이지 않도록 경계를 나눕니다.

| 예시 | 설명 |
|------|------|
| **고객 지원 BC** | 챗봇, FAQ, 티켓팅 |
| **내부 분석 BC** | 리포트 생성, 데이터 마이닝 |

---

### 팀 경계 (Conway's Law)

> 서비스 구조는 **개발 조직의 구조를 따를 때 가장 효율적**입니다.

| 팀 | 독립적 배포 영역 |
|----|-----------------|
| **모델 개발 팀** | 모델 서빙, 프롬프트 엔진 |
| **플랫폼 엔지니어링 팀** | API GW, 인증, 로깅 |

---

### RAG 데이터 소스 소유권

> 데이터의 출처가 **보안 **(HR, 재무)이나 **기술적 특성 **(실시간 로그 vs. 정적 문서)에 따라 나뉜다면, 해당 데이터를 관리하는 서비스도 분리하는 것이 **데이터 거버넌스** 측면에서 유리합니다.

| 데이터 소스 | 특성 | 권장 분리 |
|------------|------|----------|
| **HR/재무 데이터** | 고보안, 접근제한 | 별도 보안 컨텍스트 |
| **실시간 로그** | 고빈도 업데이트 | 스트리밍 파이프라인 |
| **정적 문서** |低频度 업데이트 | 배치 인덱싱 |

---

## 2. 모델 및 리소스 특성 기반 분해 (Model & Resource Context)

AI 서비스의 **운영 비용 **(OPEX)과 **하드웨어 자원의 효율성**을 극대화하기 위한 기준입니다.

### 모델 서빙 리소스 (Compute Heterogeneity)

| 리소스 타입 | 작업 유형 | 분리 효과 |
|------------|----------|----------|
| **GPU 집약적 서비스** | LLM 추론, 이미지 생성 등 고사양 GPU 필요 | 쿠버네티스 노드 셀렉터 등으로 최적화된 하드웨어에 배치 |
| **CPU/IO 집약적 서비스** | 전처리, 텍스트 파싱, 일반 API 로직 | 저비용 CPU 인스턴스 활용 |

---

### LLM 호출 빈도와 비용

| 호출 빈도 | 전략 | 효과 |
|----------|------|------|
| **높음** | 시맨틱 캐싱, 경량 모델 (SLM) 라우팅 집중 배치 | 비용 절감 |
| **낮음** | 고성능 모델 직접 호출 | 품질 우선 |

---

### 확장 요구사항 (Scalability)

> 트래픽 변동이 심한 **'사용자 인터페이스 레이어'**와 상대적으로 일정한 **'데이터 인덱싱 레이어'**를 분리하여 **독립적으로 오토스케일링**합니다.

```
┌─────────────────────────────────────────┐
│  User Interface Layer                   │
│  (트래픽 변동 심함 → 오토스케일링)      │
└─────────────────────────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│  Data Indexing Layer                    │
│  (트래픽 일정 → 고정 인스턴스)          │
└─────────────────────────────────────────┘
```

---

## 3. 운영 및 성능 기반 분해 (Operational Context)

**사용자 경험 **(UX)과 **시스템의 진화 속도**를 관리하기 위한 기준입니다.

### 변경 빈도 및 모델 업데이트 주기

| 모듈 | 변경 빈도 | 분리 효과 |
|------|----------|----------|
| **비즈니스 로직** | 자주 변경 | 독립적 배포로 민첩성 확보 |
| **핵심 추론 모델** | 가끔 변경 | 안정성 유지 |

> 모델 업데이트가 잦은 경우, **서비스 전체를 재배포하지 않고 모델 서빙 레이어만 교체**할 수 있도록 설계합니다.

---

### 추론 레이턴시 요구사항 (SLA)

| 유형 | 예시 | 통신 방식 |
|------|------|----------|
| **실시간 **(Real-time) | 채팅, 자동 완성 | 동기 방식 |
| **비실시간 **(Batch/Async) | 대량 리포트 요약, 데이터 분석 | 비동기 방식 |

#### 분리 효과

> **지연 시간에 민감한 서비스가 비실시간 작업에 의해 병목 현상을 겪지 않도록 격리 **(Bulkhead)합니다.

## 🔄 AI 서비스 분해 가이드 요약 표

| 분해 기준 | 서비스 분리 시 고려사항 | 기대 효과 |
|----------|---------------------|----------|
| **데이터 소유권** | 벡터 DB(RAG) vs. 관계형 DB(Session) 분리 | 데이터 무결성 및 보안 강화 |
| **모델 리소스** | GPU 전용 서비스 vs. CPU 일반 서비스 분리 | 인프라 비용 최적화 |
| **변경 속도** | 프롬프트 최적화 모듈 vs. 인프라 게이트웨이 분리 | 배포 민첩성 향상 (CI/CD 최적화) |
| **레이턴시** | 스트리밍 응답 서비스 vs. 배치 처리 서비스 분리 | 사용자 체감 속도 개선 및 장애 격리 |

## 💡 엔지니어링 실무 인사이트: AI 파이프라인의 '격벽' 설계

20 년 경력의 인프라 전문가 관점에서 가장 중요한 것은 **'장애 격리'**입니다.

### 모델 라우팅 서비스

> **가장 가볍고 견고하게 유지**하여, 하류의 LLM API 장애가 시스템 전체의 중단으로 이어지지 않게 해야 합니다.

```
┌─────────────┐
│  라우팅 서비스 │ ← 가볍고 견고하게
│  (최전방)    │
└──────┬──────┘
       │
       ↓
┌─────────────┐
│  LLM API    │ ← 장애 가능성
│  (하류)     │
└─────────────┘
```

---

### RAG 데이터 소스 다중화

> 특정 소스 (예: 외부 뉴스 API) 의 지연이 **전체 추론 레이턴시를 갉아먹지 않도록 비동기 또는 폴백 전략**을 반드시 포함해야 합니다.

```
RAG 소스 1 (내부 문서) ──┐
                         ├──→ 병렬 조회 → fastest 응답
RAG 소스 2 (외부 API) ──┘    (폴백 포함)
```

---

### AAR 기반 지속적 최적화

> 이 모든 지표 (**비용, 레이턴시, 호출 빈도**) 를 **AAR **(After Action Report)으로 설정하여, 분해된 서비스 간의 **통신 비용 **(Network Overhead)이 분해의 이점보다 커지지 않는지 주기적으로 점검해야 합니다.

| 지표 | 목표치 | 측정 주기 |
|------|-------|----------|
| **비용** | 토큰당 단가 | 일일 |
| **레이턴시** | p95 응답시간 | 실시간 |
| **호출 빈도** | RPM/QPM | 실시간 |
| **통신 오버헤드** | 서비스 간 네트워크 지연 | 주간 |

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 AI 서비스 MSA 분해 검토 시 고려사항:

1. **조직 - 아키텍처 정렬**: Conway's Law 기반 팀 경계와 서비스 경계 일치성
2. **리소스 격리**: GPU/CPU 리소스 분리와 비용 최적화 효과
3. **데이터 거버넌스**: RAG 데이터 소스별 보안등급과 접근통제 적절성
4. **SLA 관리**: 실시간/비실시간 서비스 분리와 레이턴시 보장
5. **장애 격리**: 모델 라우팅 서비스의 견고성과 폴백 메커니즘
6. **지속적 최적화**: AAR 지표 기반 통신 오버헤드 모니터링과 개선
