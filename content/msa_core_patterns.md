# MSA 3 대 핵심 패턴 (API GW, Service Discovery, Circuit Breaker)

마이크로서비스 아키텍처 (MSA) 환경에서 시스템의 복잡도가 증가함에 따라, 서비스 간의 원활한 소통과 안정성을 보장하기 위한 **3 대 핵심 패턴**은 인프라 설계의 필수 요소입니다.

IT 인프라 보안 및 엔지니어링 전문가 관점에서, 이 패턴들이 어떻게 시스템의 **견고함 **(Resilience)을 유지하는지 정리해 드립니다.

---

## 1. API 게이트웨이 (API Gateway)

> 시스템의 **유일한 진입점 **(Single Entry Point) 역할을 하며, 클라이언트의 요청을 적절한 마이크로서비스로 라우팅합니다.

### 주요 역할

| 역할 | 설명 |
|------|------|
| **인증 및 인가 **(Auth) | 각 서비스마다 보안 로직을 구현할 필요 없이 게이트웨이에서 통합 관리 |
| **속도 제한 **(Rate Limiting) | 특정 클라이언트의 과도한 요청을 차단하여 인프라 자원을 보호 |
| **프로토콜 변환** | 클라이언트의 HTTP 요청을 내부 서비스용 gRPC 등으로 변환 |

### AI 파이프라인 적용

> 앞서 논의한 **AI GW**가 바로 이 패턴의 변형입니다.

| 기능 | 설명 |
|------|------|
| **모델별 API 키 관리** | 각 LLM 공급자의 인증 정보를 중앙 집중화 |
| **토큰 사용량 모니터링** | 모델별 토큰 소모량을 게이트웨이에서 통합 추적 |

---

## 2. 서비스 디스커버리 (Service Discovery)

> MSA 에서는 서비스 인스턴스가 **동적으로 생성되고 소멸**됩니다 (Auto-scaling).

서비스 디스커버리는 각 서비스의 위치 (IP, Port) 를 실시간으로 관리하고 찾아주는 **'전화번호부'** 역할을 합니다.

### 방식

| 방식 | 설명 | 예시 |
|------|------|------|
| **클라이언트 사이드** | 클라이언트가 직접 디스커버리 서버에 물어보고 위치를 찾음 | Netflix Eureka |
| **서버 사이드** | 로드 밸런서가 디스커버리 서버와 통신하여 요청을 전달 | Kubernetes Service |

### 이점

> 인프라가 유연하게 확장되더라도 **서비스 간 통신 끊김 없이 동적인 주소 관리**가 가능해집니다.

```
┌─────────────┐
│  Client     │
└──────┬──────┘
       │ (요청)
       ↓
┌─────────────────────────────────┐
│   Service Discovery Server      │
│   - 인스턴스 IP/Port 관리       │
│   - 헬스체크                    │
│   - 오토스케일링 연동           │
└─────────────────────────────────┘
       ↓ (위치 반환)
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  Service A  │  │  Service B  │  │  Service C  │
│  (인스턴스 1)│  │  (인스턴스 2)│  │  (인스턴스 3)│
└─────────────┘  └─────────────┘  └─────────────┘
```

## 3. 서킷 브레이커 (Circuit Breaker)

> 특정 서비스에 장애가 발생했을 때, **장애가 전체 시스템으로 번지지 않도록 연결을 즉시 차단**하는 패턴입니다.

**누전 차단기**와 같은 원리입니다.

### 상태 변화

| 상태 | 설명 | 동작 |
|------|------|------|
| **Closed** | 정상 상태 | 요청을 통과시킴 |
| **Open** | 장애 감지 | 요청을 즉시 차단하고 **폴백 **(Fallback) 응답을 반환 |
| **Half-Open** | 복구 확인 | 일정 시간 후 일부 요청만 흘려보냄 |

```
                    ┌─────────────┐
                    │   Closed    │ ← 정상
                    └──────┬──────┘
                           │ (장애 감지)
                           ↓
                    ┌─────────────┐
                    │    Open     │ ← 차단 + 폴백
                    └──────┬──────┘
                           │ (일정 시간 경과)
                           ↓
                    ┌─────────────┐
                    │  Half-Open  │ ← 복구 확인
                    └──────┬──────┘
                           │ (성공/실패)
                           ↓
                    Closed 또는 Open
```

### 보안 및 인프라 이점

> 장애가 발생한 서비스에 계속 요청을 보내 부하를 주는 일을 막고, **시스템 전체의 가용성**을 지켜주는 **장애 격리의 핵심 도구**입니다.

## 💡 엔지니어링 실무 통찰: 패턴의 유기적 결합

이 세 패턴은 **독립적이지 않고 하나의 흐름으로 작동할 때 가장 강력**합니다.

### 통합 워크플로우

```
1. 사용자 요청이 API GW 에 도착
        ↓
2. 게이트웨이는 Service Discovery 를 통해
   현재 가용한 '추론 서비스'의 주소를 찾음
        ↓
3. 만약 추론 서비스가 응답 지연 상태라면?
        ↓
   게이트웨이에 설치된 Circuit Breaker 가 작동
        ↓
4. 사용자에게 "잠시 후 다시 시도해 주세요"라는
   안전한 메시지 (Fallback) 를 즉시 반환
```

### PDCA 사이클과의 연계

> 이러한 설계는 엔지니어님께서 중시하시는 **PDCA **(Plan-Do-Check-Act) 중 **'Check' 단계를 자동화**하고, 장애 발생 시 **즉각적인 'Act'를 수행**하게 하는 인프라적 장치입니다.

| PDCA 단계 | 패턴 연계 |
|----------|----------|
| **Plan** | API GW 라우팅 규칙, 서킷 브레이커 임계값 설계 |
| **Do** | 서비스 배포 및 트래픽 처리 |
| **Check** | 서킷 브레이커 상태 모니터링, Service Discovery 헬스체크 |
| **Act** | 장애 시 자동 차단 (Open), 복구 시 자동 재연결 (Closed) |

## 📊 3 대 패턴 비교 요약

| 패턴 | 주요 책임 | 위치 | 핵심 이점 |
|------|----------|------|----------|
| **API Gateway** | 진입점 통합, 인증/인가, 라우팅 | 시스템 최전방 | 보안 통합, 프로토콜 추상화 |
| **Service Discovery** | 동적 서비스 위치 관리 | 서비스 간 통신 | 오토스케일링 지원, 유연성 |
| **Circuit Breaker** | 장애 격리, 폴백 처리 | 서비스 호출부 | 시스템 견고함 (Resilience) |

---

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 MSA 3 대 패턴 검토 시 고려사항:

1. **API Gateway 운영**: 인증/인가 통합, Rate Limiting, 감사 로그 수집 체계
2. **Service Discovery 가용성**: 디스커버리 서버의 고가용성 (HA) 구성과 헬스체크 주기
3. **Circuit Breaker 설정**: 임계값 (실패율, 지연시간) 적절성과 폴백 응답의 안전성
4. **패턴 통합 연계**: 3 대 패턴의 유기적 연동과 종단 간 모니터링
5. **장애 대응 자동화**: 서킷 브레이커 상태 변화와 복구 프로세스의 자동화 수준
6. **PDCA 사이클**: 모니터링 기반 자동 복구와 지속적 개선 메커니즘
