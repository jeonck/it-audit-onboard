# 도메인 주도 설계 (DDD) 핵심 개념

**도메인 주도 설계 (DDD, Domain-Driven Design)**는 복잡한 소프트웨어 시스템을 구축할 때 **기술적인 구현보다 비즈니스 도메인의 본질에 집중**하는 방법론입니다.

인프라 전문가 관점에서는 시스템을 어떻게 물리적으로 분산 (MSA) 하고, 데이터 정합성을 어떻게 보장할 것인지에 대한 **설계적 근거**를 제공합니다.

요청하신 핵심 개념 3 가지를 **'주문 - 재고 - 배송'** 시나리오를 통해 정리해 드립니다.

---

## 1. 바운디드 컨텍스트 (Bounded Context, BC)

> 시스템 내에서 **특정 모델이나 용어가 유효한 경계**를 의미합니다.

같은 '상품'이나 '사용자'라는 단어도 **어느 BC 에 속하느냐에 따라 데이터 구조와 책임이 달라집니다**.

### '주문 - 재고 - 배송' 시나리오 예시

| Bounded Context | 책임 | 핵심 데이터 |
|----------------|------|------------|
| **주문 (Ordering) BC** | 사용자의 구매 의사 결정 및 결제 상태 관리 | 가격, 수량, 결제수단 |
| **재고 (Inventory) BC** | 창고 내 물품의 물리적 수량 및 가용성 관리 | SKU, 창고 위치, 입출고 이력 |
| **배송 (Shipping) BC** | 물건이 고객에게 전달되는 물리적 경로 관리 | 송장 번호, 배송지 주소, 운송사 |

---

## 2. 애그리거트 (Aggregate)

> 데이터의 일관성을 유지해야 하는 **최소한의 논리적 단위 (데이터 원자성 군집)**입니다.

각 애그리거트에는 외부와 소통하는 관문인 **애그리거트 루트 (Aggregate Root)**가 존재합니다.

### 주문 애그리거트

| 구성 요소 | 설명 |
|----------|------|
| **주문서 (Root)** | 애그리거트 루트, 외부 접근 관문 |
| **주문 항목들 (Items)** | 루트를 통해서만 접근 가능 |

#### 원칙

> 주문 항목의 수량을 변경하려면 **반드시 주문서 (Root) 를 통해서만 가능**합니다.

이를 통해 **"주문 총액은 항목들의 합과 같아야 한다"**는 데이터 정합성을 보장합니다.

### 재고 애그리거트

| 구성 요소 | 설명 |
|----------|------|
| **재고 (Root)** | 애그리거트 루트 |
| **입출고 이력** | 루트를 통해서만 접근 가능 |

### 배송 애그리거트

| 구성 요소 | 설명 |
|----------|------|
| **배송 (Root)** | 애그리거트 루트 |
| **배송 추적 기록** | 루트를 통해서만 접근 가능 |

---

## 3. 도메인 이벤트 (Domain Event)

> 도메인 내에서 발생한 **'비즈니스적으로 의미 있는 사건'**입니다.

**바운디드 컨텍스트 간의 느슨한 결합 (Loose Coupling)**을 실현하는 핵심 도구입니다.

### 발생 예시

| 이벤트 | 설명 |
|--------|------|
| **OrderPlaced** | 주문이 완료됨 |
| **PaymentApproved** | 결제가 승인됨 |

### 통신 방식

```
주문 BC 에서 결제 완료
        ↓
  OrderPaid 이벤트 발행
        ↓
┌─────────────────────────────────┐
│     이벤트 브로커 (Kafka 등)    │
└─────────────────────────────────┘
        ↓                    ↓
┌─────────────┐      ┌─────────────┐
│   재고 BC   │      │   배송 BC   │
│ (이벤트 구독)│      │ (이벤트 구독)│
│ 재고 차단   │      │ 배송 준비   │
└─────────────┘      └─────────────┘
```

---

## 🔄 주문/재고/배송 시나리오 워크플로우

| 단계 | 발생 이벤트 | 관련 BC 및 액션 |
|------|------------|----------------|
| **1. 구매** | OrderCreated | 주문 BC: 주문 애그리거트 생성 및 결제 대기 |
| **2. 결제** | PaymentApproved | 재고 BC: 이벤트를 수신하여 해당 상품 재고 차감 |
| **3. 준비** | StockReserved | 배송 BC: 이벤트를 수신하여 송장 출력 및 배송지 정보 생성 |
| **4. 발송** | DeliveryStarted | 주문 BC: 이벤트를 수신하여 사용자에게 "배송 중" 알림 발송 |

## 💡 엔지니어링 실무 인사이트: 인프라와 보안의 관점

20 년 경력의 인프라 전문가로서 DDD 를 바라볼 때 다음 두 가지가 **인프라 설계의 핵심**이 됩니다.

### 데이터베이스 분리 (Database per BC)

> 각 Bounded Context 는 **자신만의 DB**를 가져야 합니다.

| 효과 | 설명 |
|------|------|
| **장애 격리** | 주문 DB 장애가 재고 조회 장애로 이어지지 않게 격리 |
| **보안** | 인프라 보안과 가용성의 시작 |

---

### 이벤트 브로커의 중요성

> 도메인 이벤트를 전달하는 **메시지 브로커 (Kafka 등) 는 시스템의 척추**입니다.

| 요구사항 | 설명 |
|----------|------|
| **고가용성 (HA)** | 이 브로커가 다운되면 전사 서비스가 마비됨 |
| **불변 감사 로그** | 모든 이벤트의 영구 보존 필요 |

---

### 트랜잭션 관리

> 서로 다른 BC 간의 데이터 일관성은 **분산 트랜잭션 (2PC) 대신 이벤트 기반 최종 일관성 (Saga Pattern)**으로 해결하는 것이 MSA 의 정석입니다.

| 접근 방식 | 설명 |
|----------|------|
| **2PC (XA 트랜잭션)** | 강한 일관성 but 성능 저하, 복잡도 높음 |
| **Saga Pattern** | 최종 일관성 but 성능 우수, MSA 에 적합 |

```
┌─────────────────────────────────────────────────────────┐
│              Saga Pattern (예시)                        │
├─────────────────────────────────────────────────────────┤
│ 1. 주문 생성 → 2. 재고 차감 → 3. 결제 승인             │
│                          ↓                              │
│                    실패 시 보상 트랜잭션                │
│                    (주문 취소, 재고 복구)               │
└─────────────────────────────────────────────────────────┘
```

## 📊 DDD 핵심 개념 비교

| 개념 | 정의 | 목적 | 예시 |
|------|------|------|------|
| **Bounded Context** | 모델/용어가 유효한 경계 | 비즈니스 의미 분리 | 주문 BC, 재고 BC, 배송 BC |
| **Aggregate** | 데이터 일관성 단위 | 트랜잭션 경계 정의 | 주문서 + 주문항목 |
| **Domain Event** | 비즈니스 의미 사건 | BC 간 느슨한 결합 | OrderPlaced, PaymentApproved |

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 DDD 도입 검토 시 고려사항:

1. **경계 명확성**: Bounded Context 간 책임과 소유권이 명확히 분리되었는지
2. **애그리거트 설계**: 데이터 일관성 단위가 비즈니스 규칙을 올바르게 반영하는지
3. **이벤트 불변성**: 도메인 이벤트의 위변조 방지와 영구 보존 메커니즘
4. **Saga 보상 트랜잭션**: 실패 시 보상 로직의 완전성과 데이터 정합성 보장
5. **데이터베이스 격리**: Database per BC 원칙 준수와 장애 전파 방지
6. **이벤트 브로커 운영**: Kafka 등 브로커의 고가용성과 모니터링 체계
