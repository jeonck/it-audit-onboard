# A2A 협업 패턴: 오케스트레이터/파이프라인/P2P

멀티 에이전트 시스템에서 에이전트들이 어떻게 협업하는지는 시스템의 성능과 확장성을 결정하는 핵심 요소입니다.

20 년 경력의 인프라 전문가 관점에서 **확장성과 안정성**을 고려할 때 참고하실 수 있는 3 가지 주요 패턴을 정리해 드립니다.

---

## 1. 오케스트레이터 패턴 (Orchestrator Pattern)

중앙 집중식 제어 방식으로, 하나의 **'매니저' 에이전트**가 전체 작업을 분해하고 적절한 에이전트에게 할당하는 방식입니다.

### 작동 방식

```
┌─────────────────────────────────────────────────────────┐
│  오케스트레이터 패턴                                    │
├─────────────────────────────────────────────────────────┤
│                                                         │
│              ┌─────────────────┐                        │
│              │  Orchestrator   │                        │
│              │  (Manager)      │                        │
│              └────────┬────────┘                        │
│                       │                                 │
│         ┌─────────────┼─────────────┐                  │
│         ↓             ↓             ↓                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐             │
│  │ Agent A  │  │ Agent B  │  │ Agent C  │             │
│  └──────────┘  └──────────┘  └──────────┘             │
│                                                         │
│  1. 사용자 요청 → 오케스트레이터                        │
│  2. 작업 분해 → Agent Card 참조 → 할당                 │
│  3. 결과 취합 → 최종 응답                              │
└─────────────────────────────────────────────────────────┘
```

> 사용자의 요청이 들어오면 **오케스트레이터가 Agent Card 를 참조**하여 작업을 나눕니다. 각 에이전트의 결과를 취합하여 최종 응답을 만듭니다.

---

### 특징

| 장점 | 단점 |
|------|------|
| 흐름 제어가 명확함 | 오케스트레이터가 병목 지점 (SPOF) |
| 에러 처리가 쉬움 | 중앙 집중식 부하 |
| 작업 우선순위 실시간 조정 가능 | 오케스트레이터 장애 시 전체 마비 |

---

### 적합한 사례

| 시나리오 | 설명 |
|----------|------|
| **인프라 장애 대응** | 복잡한 의사결정이 필요하거나, 작업의 우선순위를 실시간으로 조정해야 하는 경우 |
| **다단계 워크플로우** | 순서와 의존성이 명확한 작업 |
| **권한 관리 중요** | 중앙에서 권한과 접근을 통제해야 하는 경우 |

---

## 2. 파이프라인 패턴 (Pipeline Pattern)

작업이 **순차적으로 진행되는 선형 구조**로, 한 에이전트의 출력이 다음 에이전트의 입력이 되는 방식입니다.

### 작동 방식

```
┌─────────────────────────────────────────────────────────┐
│  파이프라인 패턴                                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐          │
│  │ Agent A  │ →  │ Agent B  │ →  │ Agent C  │          │
│  │ 데이터   │    │ 취약점   │    │ 리포트   │          │
│  │ 수집     │    │ 분석     │    │ 생성     │          │
│  └──────────┘    └──────────┘    └──────────┘          │
│                                                         │
│  데이터 흐름: A → B → C (단방향)                       │
└─────────────────────────────────────────────────────────┘
```

> **에이전트 A(데이터 수집) → 에이전트 B(취약점 분석) → 에이전트 C(리포트 생성)**과 같이 정해진 순서대로 데이터가 흐릅니다.

---

### 특징

| 장점 | 단점 |
|------|------|
| 구조가 단순함 | 중간 단계 실패 시 전체 흐름 막힘 |
| 예측 가능 | 병목 구간 발생 가능 |
| 디버깅이 용이 | 유연성 낮음 |

---

### 적합한 사례

| 시나리오 | 설명 |
|----------|------|
| **인프라 점검 리포트** | 매일 아침 수행하는 정기적인 작업 |
| **보안 스캔 워크플로** | 정해진 순서대로 진행되는 스캔 |
| **데이터 처리 파이프라인** | ETL(추출·변환·적재) 작업 |

---

## 3. 피어투피어 패턴 (Peer-to-Peer / Choreography)

**중앙 통제 없이 에이전트들이 직접 소통**하며 자율적으로 협업하는 방식입니다.

### 작동 방식

```
┌─────────────────────────────────────────────────────────┐
│  피어투피어 (P2P) 패턴                                  │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────┐         ┌──────────┐                     │
│  │ Agent A  │ ←─────→ │ Agent B  │                     │
│  └────┬─────┘    A2A  └────┬─────┘                     │
│       │      Protocol      │                           │
│       │         ↖         ↗│                           │
│       │           ↖     ↗  │                           │
│       ↓             ↖ ↗    ↓                           │
│  ┌──────────┐    ┌──────────┐                          │
│  │ Agent C  │ ←→ │ Agent D  │                          │
│  └──────────┘    └──────────┘                          │
│                                                         │
│  - 중앙 통제 없음                                      │
│  - 에이전트 간 직접 통신 (A2A)                         │
│  - 자율적 작업 위임                                    │
└─────────────────────────────────────────────────────────┘
```

> 에이전트들이 **A2A 프로토콜을 사용하여 서로의 상태를 공유**하고, 필요한 경우 직접 작업을 위임하거나 도움을 요청합니다.

---

### 특징

| 장점 | 단점 |
|------|------|
| 매우 유연함 | 시스템 전체 상태 추적 (Observability) 어려움 |
| 확장성 높음 | 디버깅 복잡 |
| 장애 허용 (Fault Tolerance) | 특정 에이전트 불능 시 다른 에이전트가 역할 대체 |

---

### 적합한 사례

| 시나리오 | 설명 |
|----------|------|
| **마이크로서비스 자동 복구** | 동적으로 변화하는 환경의 자동 복구 시스템 |
| **Vibe Coding 환경** | 다각도의 창의적 문제 해결이 필요한 경우 |
| **분산 분석 시스템** | 여러 에이전트가 협력하여 복잡한 문제 해결 |

---

## 4. 협업 패턴 비교표

20 년 경력의 인프라 전문가로서 시스템의 확장성과 안정성을 고려할 때 참고하실 수 있는 비교 지표입니다.

| 항목 | 오케스트레이터 (Orchestrator) | 파이프라인 (Pipeline) | 피어투피어 (P2P) |
|------|------------------------------|---------------------|-----------------|
| **제어 방식** | 중앙 집중형 (Top-down) | 순차형 (Linear) | 분산형 (Decentralized) |
| **복잡도** | 중간 | 낮음 | 높음 |
| **유연성** | 중간 (매니저 로직에 종속) | 낮음 | 매우 높음 |
| **확장성** | 중간 | 중간 | 높음 |
| **주요 통신 표준** | MCP / Task Delegation | State Handoff | A2A / Agent Card |
| **비유** | 지휘자와 오케스트라 | 공장 컨베이어 벨트 | 재즈 밴드의 즉흥 연주 |
| **SPOF 리스크** | 높음 (오케스트레이터) | 중간 (각 단계) | 낮음 |
| **디버깅** | 쉬움 | 매우 쉬움 | 어려움 |
| **장애 허용** | 낮음 | 낮음 | 높음 |

## 💡 엔지니어링 제언: 하이브리드 접근법

현실적인 고성능 시스템은 보통 **이 패턴들을 혼합**하여 사용합니다.

### 전략

```
┌─────────────────────────────────────────────────────────┐
│  하이브리드 협업 아키텍처                               │
├─────────────────────────────────────────────────────────┤
│                                                         │
│              ┌─────────────────┐                        │
│              │  Orchestrator   │  ← 전체 큰 흐름 제어  │
│              └────────┬────────┘                        │
│                       │                                 │
│         ┌─────────────┼─────────────┐                  │
│         ↓             ↓             ↓                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐             │
│  │Pipeline  │  │  P2P     │  │Pipeline  │             │
│  │(반복작업)│  │(예외/분석)│  │(정제)    │             │
│  └──────────┘  └──────────┘  └──────────┘             │
│                                                         │
│  - 전체적인 큰 흐름: 오케스트레이터                    │
│  - 특정 반복 작업 (데이터 정제 등): 파이프라인         │
│  - 예외적 장애/고도 분석: 에이전트 간 P2P 협업         │
└─────────────────────────────────────────────────────────┘
```

---

### 하이브리드 아키텍처 예시: 인프라 장애 대응

| 단계 | 패턴 | 설명 |
|------|------|------|
| **1. 장애 감지** | 파이프라인 | 모니터링 → 알림 → 로그 수집 (순차) |
| **2. 원인 분석** | P2P | 로그 에이전트 ↔ 메트릭 에이전트 ↔ 설정 에이전트 협업 |
| **3. 대응 결정** | 오케스트레이터 | 우선순위 결정, 자원 할당 |
| **4. 복구 실행** | 파이프라인 | 백업 → 재배포 → 검증 (순차) |
| **5. 사후 분석** | P2P | 여러 에이전트가 협력하여 8D 보고서 생성 |

---

## 📋 패턴 선택 가이드

| 상황 | 권장 패턴 | 이유 |
|------|----------|------|
| **명확한 워크플로우** | 파이프라인 | 단순하고 예측 가능 |
| **중앙 통제 필요** | 오케스트레이터 | 권한 관리, 우선순위 조정 |
| **창의적 문제 해결** | P2P | 유연성과 자율성 중요 |
| **대규모 시스템** | 하이브리드 | 각 패턴의 장점 활용 |
| **고가용성 요구** | P2P | 장애 허용 (Fault Tolerance) |
| **감사 추적 중요** | 오케스트레이터 | 중앙 집중식 로그 |

---

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 A2A 협업 패턴 검토 시 고려사항:

1. **제어 구조 명확성**: 오케스트레이터의 권한과 책임 범위 정의
2. **단일 장애점 (SPOF)**: 오케스트레이터 장애 시 페일오버 메커니즘
3. **감사 추적성**: P2P 패턴에서 분산 로그의 통합과 추적 가능성
4. **확장성 계획**: 에이전트 추가 시 패턴별 확장 전략
5. **디버깅 용이성**: 파이프라인은 단계별 로그, P2P 는 분산 트레이싱
6. **하이브리드 복잡도**: 패턴 혼합 시 인터페이스와 경계 명확화
