# AI Observability: AI 시스템 관측 가능성

**AI Observability**(관측 가능성)는 기존 소프트웨어의 모니터링 (APM, Log) 과는 차원이 다른 도전 과제입니다.

전통적인 시스템이 **"서버가 살아있는가?**(Availability)를 확인했다면, AI Observability 는 **"모델이 제정신인가?**(Reliability & Validity)를 실시간으로 추적하는 기술입니다.

---

## 1. AI Observability 의 핵심 요소 (3 Pillars)

AI 시스템은 결정론적이지 않기 때문에 다음 세 가지를 **통합적으로 관측**해야 합니다.

### Inference Observability (추론 관측)

> **입력 **(Prompt)을 기록하고, 모델이 왜 그런 답변을 내놓았는지 **추론 과정을 추적**합니다. (Traceability)

| 관측 항목 | 설명 |
|----------|------|
| **Prompt/Response 쌍** | 모든 입출력 기록 보존 |
| **추론 과정** | Chain-of-Thought, Tool Call 이력 |
| **의사결정 근거** | RAG 참조 문서, Agent 판단 이유 |

---

### Data & Model Drift (데이터 및 모델 변화)

> **학습 당시의 데이터 분포**와 **실제 유입되는 데이터의 차이**를 감지합니다. 모델 업데이트 후 성능이 미세하게 저하되는 현상을 포착합니다.

| 드리프트 유형 | 설명 |
|--------------|------|
| **Data Drift** | 입력 데이터 분포 변화 감지 |
| **Model Drift** | 모델 업데이트 후 성능 변화 |
| **Concept Drift** | 비즈니스 맥락 변화로 인한 성능 저하 |

---

### System Performance (인프라 성능)

> **토큰 소모량, GPU VRAM 점유율, 콜드스타트 지연 시간**, 그리고 가장 중요한 **'토큰당 비용'**을 모니터링합니다.

| 지표 | 설명 |
|------|------|
| **토큰 소모량** | 입력/출력 토큰 수, 세션별 누적 |
| **GPU VRAM** | 메모리 점유율, OOM 위험 감지 |
| **Latency** | 콜드스타트, TTFT(Time-to-First-Token) |
| **Cost** | 토큰당 비용, 세션별/에이전트별 비용 |

---

## 2. 해결하고 싶은 핵심 페인 포인트 (Pain Points)

엔지니어님께서 설계하시는 **폐쇄형 AI 시스템**이나 **멀티에이전트 **(MiroFish) 환경에서 특히 해결해야 할 4 가지 사항입니다.

---

### ① 환각 (Hallucination) 및 품질 저하 감지

#### 문제

> AI 가 그럴듯한 거짓말을 하거나, 어제까지 잘 되던 프롬프트가 모델 업데이트 후 엉뚱한 답을 내놓는 경우.

#### 해결

> **RAG 검수 **(Retrieval Score)를 통해 모델이 참조한 문서와 답변의 **일치도를 수치화 **(Faithfulness)하고, 사용자 피드백 (Thumbs up/down) 과 연동하여 **실시간 품질 점수**를 산출합니다.

```
┌─────────────────────────────────────────────────────────┐
│  환각 감지 파이프라인                                   │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  1. RAG Retrieval → 참조 문서 추출                     │
│         ↓                                               │
│  2. Faithfulness Score 계산 (0~100)                    │
│         ↓                                               │
│  3. 임계치 미만 (예: 70 점) → 경고 발생                │
│         ↓                                               │
│  4. 사용자 피드백 (👍/👎) 과 연동 → 품질 점수 갱신    │
└─────────────────────────────────────────────────────────┘
```

| 지표 | 설명 |
|------|------|
| **Faithfulness Score** | 참조 문서 대비 답변 일치도 (0~100) |
| **Hallucination Rate** | 환각 발생 빈도 (%) |
| **User Feedback Score** | 사용자 만족도 (👍/👎 비율) |

---

### ② 컨텍스트 위생 및 비용 제어 (Context Hygiene & Cost)

#### 문제

> 에이전트가 **무한 루프**에 빠지거나, **불필요하게 긴 HTML 전체**를 컨텍스트에 넣어 비용이 급증하는 경우.

#### 해결

> **agent-browser**와 같은 툴의 효율성을 추적하고, **세션별 토큰 사용량에 쿼터 **(Quota)를 설정하여 임계치 초과 시 알람을 발생시킵니다.

```
┌─────────────────────────────────────────────────────────┐
│  컨텍스트 비용 제어                                     │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  세션별 토큰 쿼터 설정                                  │
│  - 일일 제한: 100,000 tokens                           │
│  - 경고: 80% 도달 시 알림                              │
│  - 차단: 100% 초과 시 추가 요청 거부                  │
│                                                         │
│  agent-browser 효율성 추적                             │
│  - HTML 전체 vs 접근성 트리 크기 비교                  │
│  - 토큰 절감률: 90% 목표                               │
└─────────────────────────────────────────────────────────┘
```

| 지표 | 설명 |
|------|------|
| **Token Quota Usage** | 세션별 토큰 사용량 (%) |
| **Context Bloat Rate** | 불필요한 컨텍스트 비율 |
| **Cost per Session** | 세션별 비용 |
| **Infinite Loop Detection** | 무한 루프 감지 |

---

### ③ 에이전트 협업의 투명성 (Agent-to-Agent Tracing)

#### 문제

> 멀티에이전트 시스템에서 **"누가 잘못해서 장애가 났는가?"**를 파악하기 어렵습니다. (A2A 통신의 블랙박스화)

#### 해결

> **Agent Card 와 연동된 분산 트레이싱**을 통해 에이전트 간의 메시지 교환 흐름을 시각화합니다. 어떤 에이전트의 판단이 연쇄 오류를 일으켰는지 파악합니다.

```
┌─────────────────────────────────────────────────────────┐
│  A2A 분산 트레이싱                                      │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐          │
│  │ Agent A  │ →  │ Agent B  │ →  │ Agent C  │          │
│  │ (오류)   │    │ (전파)   │    │ (실패)   │          │
│  └──────────┘    └──────────┘    └──────────┘          │
│       ↑               ↑               ↑                 │
│  Trace ID: abc123  Trace ID: abc123  Trace ID: abc123  │
│                                                         │
│  → Trace ID 로 연쇄 오류 추적 가능                     │
└─────────────────────────────────────────────────────────┘
```

| 지표 | 설명 |
|------|------|
| **Trace ID** | A2A 통신 종단 간 추적 ID |
| **Agent Handoff Count** | 에이전트 간 위임 횟수 |
| **Error Propagation Path** | 오류 전파 경로 |
| **Root Cause Agent** | 근본 원인 에이전트 |

---

### ④ 보안 및 컴플라이언스 (Data Leakage)

#### 문제

> **민감 정보 **(PII)가 모델 외부로 유출되거나, **부적절한 프롬프트 주입 **(Injection)이 시도되는 경우.

#### 해결

> **입력/출력 가드레일 통과 여부**를 실시간 로그로 남기고, 보안 정책 위반 시 즉시 차단하는 **'실시간 감사 로그 **(Real-time Audit Trail)를 구축합니다.

```
┌─────────────────────────────────────────────────────────┐
│  실시간 감사 로그                                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  입력 가드레일 검사                                    │
│  - PII 감지 (주민번호, 전화번호, 이메일)              │
│  - 프롬프트 인젝션 감지                                │
│  - 위반 시 차단 + 로그 기록                            │
│                                                         │
│  출력 가드레일 검사                                    │
│  - 민감 정보 유출 감지                                 │
│  - 부적절한 콘텐츠 필터링                              │
│  - 위반 시 차단 + 관리자 알림                          │
└─────────────────────────────────────────────────────────┘
```

| 지표 | 설명 |
|------|------|
| **PII Detection Rate** | 민감 정보 감지 횟수 |
| **Prompt Injection Attempts** | 프롬프트 인젝션 시도 횟수 |
| **Guardrail Violations** | 가드레일 위반 횟수 |
| **Audit Trail Completeness** | 감사 로그 완전성 |

---

## 3. 인프라 전문가를 위한 설계 제언: PDCA 기반 운영

AI Observability 는 단순히 대시보드를 보는 것이 아니라, **품질 개선의 선순환**을 만드는 도구가 되어야 합니다.

### Plan

> 각 에이전트와 모델의 **기대 성능 지표 **(SLA)를 정의합니다.

| 항목 | 예시 |
|------|------|
| **Latency SLA** | p95 < 2 초 |
| **Faithfulness** | > 90 점 |
| **Token Budget** | 일일 100,000 tokens/에이전트 |
| **Hallucination Rate** | < 1% |

---

### Do

> **OpenTelemetry**와 같은 표준을 활용하여 AI 로그를 수집합니다.

```yaml
# OpenTelemetry AI 로그 수집 설정
receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  batch:
  attributes:
    add:
      ai_provider: "anthropic"
      ai_model: "claude-sonnet-4-20250514"

exporters:
  logging:
  otlphttp:
    endpoint: "https://observability.example.com/v1/traces"
```

---

### Check

> **AAR **(After Action Report)를 통해 AI 의 답변 실패 사례를 분석합니다.

| 분석 항목 | 설명 |
|----------|------|
| **실패 사례 분류** | 환각, 컨텍스트오염, 에이전트오류, 보안위반 |
| **근본 원인 분석** | 5 Why 분석 |
| **영향도 평가** | 사용자 영향, 비용 영향, 보안 영향 |
| **재발 방지 대책** | 프롬프트수정, 모델교체, 가드레일강화 |

---

### Act

> 분석 결과를 바탕으로 **프롬프트를 수정**하거나, **더 작은 모델 **(SLM)하여 비용을 최적화합니다.

| 개선 액션 | 설명 |
|----------|------|
| **프롬프트 수정** | 실패 사례 기반 프롬프트 개선 |
| **모델 교체** | 고비용 모델 → SLM (비용 90% 절감) |
| **가드레일 강화** | 새로운 위반 패턴 반영 |
| **에이전트 재구성** | 협업 패턴 최적화 |

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 AI Observability 도입 검토 시 고려사항:

1. **추적 가능성**: Prompt/Response 쌍과 추론 과정의 완전한 기록 보존
2. **품질 지표**: Faithfulness, Hallucination Rate 등 AI 특화 지표 정의
3. **비용 통제**: 토큰 쿼터, 세션별 비용, 에이전트별 예산 관리
4. **보안 감사**: PII 감지, 프롬프트인젝션, 가드레일 위반 실시간 로그
5. **A2A 투명성**: 멀티에이전트 간 분산 트레이싱과 근본 원인 분석
6. **PDCA 사이클**: AAR 자동화와 지속적 개선 프로세스 운영
