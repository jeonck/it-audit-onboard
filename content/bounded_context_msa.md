# Bounded Context 와 MSA 서비스 경계 설계

마이크로서비스 아키텍처 (MSA) 를 설계할 때 **Bounded Context**는 시스템을 어떤 단위로 쪼갤 것인가를 결정하는 가장 중요한 전략적 설계 도구입니다.

**도메인 주도 설계 (DDD, Domain-Driven Design)**에서 파생된 이 개념은 단순히 기술적인 분리가 아닌, **비즈니스 의미의 경계**를 정의하는 데 중점을 둡니다.

20 년 경력의 인프라 및 보안 전문가 관점에서 볼 때, Bounded Context 를 명확히 정의하는 것은 **장애 전파 차단**과 **데이터 무결성 확보**의 핵심입니다.

---

## 1. Bounded Context 란?

> 특정 모델이 특정한 의미를 가지고 적용되는 **제한된 경계**를 의미합니다.

같은 용어라도 **어느 컨텍스트에 있느냐에 따라 그 의미와 데이터 구조가 달라질 수 있음**을 인정하는 것이 핵심입니다.

### 예시: '상품 (Product)'이라는 단어

| 컨텍스트 | 중요한 속성 |
|----------|------------|
| **판매 컨텍스트** | 가격, 재고, 상품 설명, 카테고리 |
| **배송 컨텍스트** | 무게, 부피, 출발지/도착지 주소, 배송 상태 |
| **AS 컨텍스트** | 보증 기간, 수리 이력, 부품 호환성 |

---

## 2. 서비스 경계를 나누는 4 가지 핵심 기준

### ① 언어적 경계 (Ubiquitous Language)

> 팀원들이 사용하는 **용어가 달라지는 지점**이 곧 경계입니다.

| 신호 | 설명 |
|------|------|
| **질문 발생** | "여기서 말하는 '사용자'가 결제자입니까, 아니면 실제 서비스를 이용하는 사람입니까?" |
| **의미** | 그 지점이 두 개의 Bounded Context 로 나뉘어야 할 신호 |

---

### ② 업무 프로세스 및 조직 구조 (Conway's Law)

> **실제 비즈니스를 수행하는 팀 단위**로 경계를 나눕니다.

| 상황 | 권장 접근 |
|------|----------|
| 결제 팀과 배송 팀 분리 | 각 팀이 독립적으로 자신의 도메인을 관리하도록 서비스 분리 |
| **효과** | 배포 및 운영 효율성 면에서 유리 |

---

### ③ 데이터 소유권 및 생명주기

> 데이터가 **생성되고 소멸되는 생명주기**가 다른 경우 분리합니다.

| 데이터 유형 | 생명주기 | 권장 처리 |
|------------|---------|----------|
| **주문 데이터** | 생성 → 결제 완료 → 상태 변화 | 트랜잭션 중심 |
| **로그 데이터** | 생성 → 읽기 전용 → 일정 기간 후 삭제 | 이벤트 소싱 |

> 이 둘은 서로 다른 경계에 두는 것이 **데이터 관리 측면**에서 효율적입니다.

---

### ④ 변경의 속도와 이유 (Single Responsibility)

> **변경되는 빈도나 이유가 다른 기능**을 분리합니다.

| 모듈 | 변경 특성 | 권장 처리 |
|------|----------|----------|
| **AI 추론 모듈** | 프롬프트 자주 튜닝 | 빠른 배포 사이클 |
| **보안 감사 모듈** | 규정 준수 위해 엄격히 관리 | 느린 배포 사이클 |

> 서로 다른 속도로 진화하므로 **경계를 나누는 것이 좋습니다**.

---

## 3. Bounded Context 간 통신 전략 (Context Mapping)

경계를 나눈 후에는 이들 사이를 **어떻게 연결할지**가 인프라 설계의 핵심이 됩니다.

### Shared Kernel

> 두 컨텍스트가 **공통 데이터 구조를 공유**

| 특징 | 설명 |
|------|------|
| **장점** | 중복 코드 감소 |
| **단점** | 결합도가 높아 주의 필요 |

---

### Customer-Supplier

> 한쪽이 데이터를 제공하고 다른 쪽이 소비하는 관계

```
┌──────────────┐         ┌──────────────┐
│   Supplier   │ ──────→ │   Customer   │
│  (데이터 제공)│         │  (데이터 소비)│
└──────────────┘         └──────────────┘
```

---

### Anticorruption Layer (ACL)

> **외부 시스템이나 레거시 시스템의 복잡한 모델이 내 도메인을 오염시키지 않도록** 중간에 변환 계층을 두는 방식

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│  레거시 시스템 │ ──────→ │      ACL     │ ──────→ │  내 도메인   │
│  (복잡한 모델)│         │  (변환 계층)  │         │  (깨끗한 모델)│
└──────────────┘         └──────────────┘         └──────────────┘
```

> **AI 파이프라인의 AI Gateway**가 이 역할을 수행하기도 합니다.

## 💡 엔지니어링 실무 통찰: Bounded Context 와 보안/인프라

보안 및 인프라 설계 시 Bounded Context 는 다음과 같은 가치를 제공합니다.

### 최소 권한 원칙 (Least Privilege)

| 효과 | 설명 |
|------|------|
| **자원 제한** | 각 컨텍스트 (서비스) 별로 접근할 수 있는 DB 와 인프라 자원을 엄격히 제한 |
| **사고 격리** | 보안 사고 발생 시 피해를 해당 경계 내로 격리 |

---

### 데이터 독립성

> 각 Bounded Context 는 **자기만의 DB**를 가집니다 (**Database per Service**).

| 효과 | 설명 |
|------|------|
| **스키마 변경** | 데이터베이스 스키마 변경이 다른 서비스의 장애로 이어지는 상황 방지 |
| **운영 안정성** | 서비스 간 영향도 최소화 |

---

### PDCA 기반 튜닝

| 상황 | 대응 |
|------|------|
| 특정 컨텍스트에서 성능 병목 발생 | 전체 시스템을 건드리지 않고 해당 Bounded Context 내의 아키텍처만 집중적으로 개선 |
| 환각 현상 잦음 | RAG 로직 등 해당 컨텍스트만 개선하는 **AAR 수행** |

## 🎯 Compound AI System 의 Bounded Context 예시

| Bounded Context | 책임 | 포함 서비스 |
|----------------|------|------------|
| **입력 처리** | 사용자 입력 검증, PII 마스킹 | 입력 가드레일, 의도 분류기 |
| **추론 처리** | LLM 추론, 프롬프트 관리 | 모델 라우터, 프롬프트 엔진 |
| **지식 처리** | RAG, 벡터 DB 관리 | 검색 서비스, 인덱싱 서비스 |
| **출력 처리** | 출력 검증, 구조화 | 출력 가드레일, 포맷팅 서비스 |
| **감사/모니터링** | 로깅, 분석, AAR | 감사 로그, 성능 분석, AAR 생성 |

---

## 🤔 설계 검토 질문

> 설계하신 **Compound AI System**에서 '가드레일'과 'RAG'를 **별도의 Bounded Context**로 보시는지, 아니면 하나의 거대한 **'신뢰 영역'**으로 묶고 계신가요?

이 경계를 어떻게 설정하느냐에 따라 **서비스 간 이벤트 설계의 복잡도**가 달라질 수 있습니다.

---

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 Bounded Context 설계 검토 시 고려사항:

1. **경계 명확성**: 서비스 간 책임과 소유권이 명확히 분리되었는지
2. **용어 일관성**: 각 컨텍스트 내 Ubiquitous Language 가 일관되게 사용되고 있는지
3. **데이터 독립성**: Database per Service 원칙 준수와 데이터 소유권 명확성
4. **ACL 운영**: 레거시/외부 시스템 연동 시 Anticorruption Layer 적절성
5. **보안 격리**: 최소 권한 원칙과 컨텍스트 간 접근 통제 적절성
6. **변경 격리**: 변경 속도가 다른 모듈의 경계 분리와 독립적 배포 가능성
