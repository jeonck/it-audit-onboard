# REST API vs MCP Tool Calling: 유연성의 차이

기존 REST API 방식이 **"결정론적 하드코딩"**이라면, MCP 기반의 툴 호출은 **"비결정론적 자율 판단"**에 기반합니다.

이 차이가 가져오는 강력함을 **'인프라 보안 장애 대응'** 시나리오를 예시로 들어 설명해 드리겠습니다.

---

## 1. 기존 REST API 방식: "고정된 시나리오"

개발자가 발생 가능한 모든 상황을 예측하고 **if-else 또는 switch-case 로 로직을 짜야 합니다**.

### 상황: 서버 CPU 부하 급증 발생

```python
# 기존 REST API 방식 - 하드코딩된 로직
def handle_cpu_spike():
    # 1. GET /metrics 호출하여 임계치 확인
    metrics = requests.get("http://server/metrics")
    cpu_usage = metrics.json()['cpu']
    
    # 2. CPU > 90% 이면 POST /restart-service 호출
    if cpu_usage > 90:
        requests.post("http://server/restart-service")
        return "서비스 재시작 완료"
    else:
        return "정상 범위"
```

### 한계

> 만약 부하의 원인이 **'서비스 장애'**가 아니라 **'디도스 (DDoS) 공격'**이거나 **'DB 락'** 때문이라면, 미리 짜놓은 '재시작' 로직은 **오히려 상황을 악화**시킬 수 있습니다.

즉, **예외 상황에 대한 유연성이 제로에 가깝습니다**.

```
┌─────────────────────────────────────────────────────────┐
│  REST API 방식의 한계                                   │
├─────────────────────────────────────────────────────────┤
│  CPU 급증 → 무조건 재시작                               │
│                                                         │
│  실제 원인이...                                         │
│  - DDoS 공격 → 재시작해도 소용 (공격 계속)             │
│  - DB 락 → 재시작해도 락 유지 (재발생)                 │
│  - 메모리 누수 → 재시작하면 일시 해결 (근본원인 미해결)│
│                                                         │
│  → 개발자가 모든 경우의 수를 예측하여 코딩해야 함       │
└─────────────────────────────────────────────────────────┘
```

---

## 2. MCP 툴 호출 방식: "맥락 기반의 도구 선택"

MCP 는 LLM 에게 여러 가지 **'도구 **(Tools)를 던져주고, **현재 상황 **(Context)에 가장 적합한 도구를 **LLM 이 스스로 판단하여 조합**하게 합니다.

### 상황: 동일한 서버 CPU 부하 급증 발생

### LLM 의 사고 과정 (MCP 환경)

```
┌─────────────────────────────────────────────────────────┐
│  LLM 의 자율적 판단 과정                                │
├─────────────────────────────────────────────────────────┤
│  "음, CPU 가 높군. 우선 list_processes 툴로             │
│   범인을 찾아야겠어."                                   │
│                                                         │
│  (결과 확인 후)                                         │
│  "범인은 특정 IP 에서의 과도한 요청이네?               │
│   단순 재시작보다는 block_ip 툴과                       │
│   check_security_logs 툴을 먼저 써야겠어."             │
│                                                         │
│  (보안 로그 확인 후)                                    │
│  "이건 단순 공격이 아니라 설정 오류에 의한 루프야.     │
│   update_config 툴로 수정한 뒤 reload 할게."           │
└─────────────────────────────────────────────────────────┘
```

### MCP Tool Call 흐름

```json
// 1. 프로세스 목록 확인
{
  "method": "tools/call",
  "params": {
    "name": "list_processes",
    "arguments": {"sort_by": "cpu"}
  }
}

// 2. 보안 로그 확인
{
  "method": "tools/call",
  "params": {
    "name": "check_security_logs",
    "arguments": {"time_range": "last_1h"}
  }
}

// 3. IP 차단
{
  "method": "tools/call",
  "params": {
    "name": "block_ip",
    "arguments": {"ip": "192.168.1.100", "duration": "1h"}
  }
}

// 4. 설정 수정
{
  "method": "tools/call",
  "params": {
    "name": "update_config",
    "arguments": {"key": "retry_loop", "value": "false"}
  }
}

// 5. 서비스 리로드
{
  "method": "tools/call",
  "params": {
    "name": "reload_service",
    "arguments": {}
  }
}
```

### 강력함의 핵심

> 개발자가 **"IP 공격이면 A 를 하고, 설정 오류면 B 를 하라"**고 일일이 코딩하지 않았음에도, LLM 이 **MCP 서버가 제공하는 Resources**(로그)를 활용해 **최적의 솔루션을 실시간으로 구성**합니다.

---

## 3. MCP 의 유연성이 주는 3 가지 혁신

### ① 도구의 추상화 (N:M 해결)

| 방식 | 설명 |
|------|------|
| **기존 REST** | Slack 에 알림 → Slack API 공부<br>Jira 티켓 → Jira API 공부<br>각각 별도 코딩 필요 |
| **MCP** | "Slack 에 현재 상황 보고하고<br>Jira 티켓 생성해줘" |

> MCP 환경에서는 **자연어 한마디**면 LLM 이 등록된 MCP 서버들 사이에서 필요한 툴을 알아서 골라 호출합니다.

```
┌─────────────────────────────────────────────────────────┐
│  MCP 도구 추상화                                        │
├─────────────────────────────────────────────────────────┤
│  사용자: "Slack 에 보고하고 Jira 티켓 만들어줘"        │
│                    ↓                                    │
│  ┌──────────────────────────────────────────┐          │
│  │  LLM 자율 판단                            │          │
│  │  1. Slack MCP Server → send_message 호출 │          │
│  │  2. Jira MCP Server → create_ticket 호출 │          │
│  └──────────────────────────────────────────┘          │
│                    ↓                                    │
│  ✅ Slack 알림 전송 완료                                │
│  ✅ Jira 티켓 생성 완료 (TKT-123)                       │
└─────────────────────────────────────────────────────────┘
```

---

### ② 다단계 추론 (Multi-step Reasoning)

| 방식 | 특징 |
|------|------|
| **REST API** | 한 번의 호출로 끝나는 경우 많음 |
| **MCP** | **호출 → 결과 확인 → 다음 도구 판단** 루프 |

> 이는 엔지니어님께서 운영하시는 **MiroFish/BettaFish 같은 에이전트**가 **"생각하며 일하는"** 구조를 가능케 하는 핵심 엔진입니다.

```
┌─────────────────────────────────────────────────────────┐
│  MCP 다단계 추론 루프                                   │
├─────────────────────────────────────────────────────────┤
│  1. Tool Call → 결과 수신                               │
│         ↓                                               │
│  2. 결과 분석 → 다음 행동 판단                          │
│         ↓                                               │
│  3. Tool Call → 결과 수신                               │
│         ↓                                               │
│  4. ... (목표 달성 시까지 반복)                        │
└─────────────────────────────────────────────────────────┘
```

---

### ③ 컨텍스트 주입의 용이성

MCP 는 단순 툴 호출뿐만 아니라 **Resources**를 통해 모델이 **"공부할 자료"**를 실시간으로 넘겨줍니다.

| 방식 | 예시 |
|------|------|
| **REST** | "이 에러 메시지 해석해줘."<br>→ 지식 부족으로 환각 발생 가능 |
| **MCP** | "MCP 서버에서 latest_security_patch_notes 를 읽어온 뒤,<br>이 에러와 대조해서 해결해줘."<br>→ 정확한 근거 기반 해결 |

```
┌─────────────────────────────────────────────────────────┐
│  MCP 컨텍스트 주입                                      │
├─────────────────────────────────────────────────────────┤
│  1. MCP Server → Resources 읽기                         │
│     - latest_security_patch_notes                       │
│     - error_code_database                               │
│     - system_config                                     │
│                    ↓                                    │
│  2. LLM 이 읽은 자료를 바탕으로 추론                   │
│                    ↓                                    │
│  3. 근거 기반 해결책 제시                              │
│     "이 에러는 보안 패치 X 와 관련이 있습니다..."       │
└─────────────────────────────────────────────────────────┘
```

## 📊 REST API vs MCP Tool Calling 비교

| 항목 | REST API | MCP Tool Calling |
|------|----------|-----------------|
| **접근 방식** | 결정론적 (하드코딩) | 비결정론적 (자율판단) |
| **상황 대응** | 미리 정의된 시나리오만 | 실시간 맥락 기반 최적화 |
| **도구 통합** | 별도 코딩 필요 | 자연어로 자동 조합 |
| **다단계 처리** | 제한적 (체인 필요) | 네이티브 루프 지원 |
| **컨텍스트** | 수동 주입 | Resources 자동 연동 |
| **유지보수** | 시나리오 추가마다 코드 수정 | Tool 추가만 |
| **확장성** | 복잡도 기하급수적 | 복잡도 선형적 |

## 🎯 실무 적용 가이드

현재 설계 중인 시스템에서 **"특정 상황 발생 시 LLM 이 스스로 판단해야 하는 가장 복잡한 시나리오"**는 무엇인가요?

그 시나리오를 **MCP 툴셋으로 정의**하는 순간, 시스템의 지능이 한 단계 격상될 것입니다.

### MCP 툴셋 정의 예시 (인프라 장애 대응)

```json
{
  "tools": [
    {
      "name": "list_processes",
      "description": "List all running processes sorted by resource usage"
    },
    {
      "name": "check_security_logs",
      "description": "Check security logs for suspicious activity"
    },
    {
      "name": "block_ip",
      "description": "Block a specific IP address for a duration"
    },
    {
      "name": "update_config",
      "description": "Update system configuration key-value pair"
    },
    {
      "name": "reload_service",
      "description": "Reload service without full restart"
    },
    {
      "name": "send_alert",
      "description": "Send alert to Slack/Teams channel"
    }
  ]
}
```

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 REST API vs MCP Tool Calling 검토 시 고려사항:

1. **예측 가능성**: REST 는 결정론적 (감사 용이), MCP 는 비결정론적 (로그 필수)
2. **책임 소재**: REST 는 개발자 책임 명확, MCP 는 LLM 판단 과정 기록 필요
3. **감사 추적성**: MCP Tool Call 의 다단계 루프 전체 로그 보존 필수
4. **보안 통제**: MCP 자율 도구 호출의 권한 관리와 승인 프로세스
5. **테스트 전략**: REST 는 단위테스트, MCP 는 시나리오 기반 통합테스트
6. **장애 대응**: MCP 의 자율 판단이 오판할 경우의 수동 개입 (Human-in-the-loop) 메커니즘
