# 이벤트 드리븐 아키텍처 (EDA) 심화

**이벤트 드리븐 아키텍처 **(Event-Driven Architecture, EDA)는 시스템 내에서 발생하는 상태의 변화, 즉 **'이벤트 **(Event)를 중심으로 서비스들이 통신하고 동작하는 설계 방식입니다.

IT 인프라 보안 및 인프라 엔지니어링 관점에서 볼 때, EDA 는 시스템의 **유연성과 확장성**, 그리고 특히 **비가역적인 감사 로그 **(Audit Log)에 탁월한 선택입니다.

---

## 1. EDA 의 핵심 구성 요소

EDA 는 크게 세 가지 주체로 나뉩니다.

### 이벤트 생성자 (Event Producer)

> **상태 변화를 감지하고 이벤트를 발행**합니다.

| 예시 | 설명 |
|------|------|
| "사용자가 질문을 입력함" | 사용자 입력 이벤트 |
| "LLM 답변 생성 완료" | 추론 완료 이벤트 |

### 이벤트 브로커 (Event Broker)

> **생성된 이벤트를 수신하여 필요한 소비자들에게 전달**하는 중간 관리자입니다.

| 예시 | 설명 |
|------|------|
| **Kafka** | 높은 처리량, 영구 저장 |
| **RabbitMQ** | 복잡한 라우팅, 낮은 지연시간 |
| **AWS EventBridge** | 서버리스, AWS 네이티브 |

### 이벤트 소비자 (Event Consumer)

> **브로커로부터 이벤트를 전달받아 실제 비즈니스 로직**을 수행합니다.

| 예시 | 설명 |
|------|------|
| **로그 저장 서비스** | 감사 로그 기록 |
| **RAG 인덱싱 서비스** | 벡터 DB 업데이트 |

---

## 2. 주요 패턴 및 기술적 특징

### ① 비동기 메시징 (Asynchronous Messaging)

> 생성자는 이벤트를 브로커에 **던지기만 할 뿐**, 소비자가 이를 언제 처리하는지 **기다리지 않습니다**.

이는 시스템의 **느슨한 결합 **(Loose Coupling)을 가능하게 하여, 한 서비스의 장애가 전체로 번지는 것을 막아줍니다.

```
┌─────────────┐
│  Producer   │
│  (생성자)   │
└──────┬──────┘
       │ (이벤트 발행)
       ↓
┌─────────────┐
│   Broker    │ ← Non-blocking
│  (브로커)   │
└──────┬──────┘
       │ (이벤트 전달)
       ↓
┌─────────────┐
│  Consumer   │
│  (소비자)   │
└─────────────┘
```

---

### ② 이벤트 소싱 (Event Sourcing)

> 데이터의 **현재 상태만 저장**하는 것이 아니라, **발생한 모든 이벤트를 순서대로 저장**하는 방식입니다.

#### 장점

| 장점 | 설명 |
|------|------|
| **상태 복구** | 과거 어느 시점으로든 상태 복구 가능 |
| **불변 감사 추적** | 금융이나 의료 도메인에서 요구하는 Immutable 감사 로그 |

---

### ③ CQRS (Command Query Responsibility Segregation)

> **명령 **(데이터 변경)과 **조회 **(데이터 읽기)를 분리하는 패턴입니다.

이벤트를 통해 **조회 전용 DB 를 따로 업데이트**함으로써, 복잡한 AI 쿼리 성능을 비약적으로 향상시킬 수 있습니다.

```
┌─────────────────────────────────────────┐
│              CQRS 패턴                  │
├─────────────────┬───────────────────────┤
│   Command Side  │    Query Side         │
│   (쓰기 전용)   │    (읽기 전용)        │
├─────────────────┼───────────────────────┤
│ - 데이터 변경   │ - 복잡한 AI 쿼리      │
│ - 이벤트 발행   │ - 최적화된 조회       │
│ - 이벤트 소싱   │ - 별도 DB             │
└─────────────────┴───────────────────────┘
```

---

## 3. AI 파이프라인 시스템에서의 EDA 적용 사례

엔지니어님께서 설계하신 **Compound AI System**에 EDA 를 적용하면 다음과 같은 고도화가 가능합니다.

| 시나리오 | 이벤트 발생 | 구독 서비스 및 동작 |
|----------|------------|-------------------|
| **비동기 로깅** | 응답 반환 완료 | 감사 로그 서비스가 구독하여 **불변 로그**로 기록 |
| **실시간 성능 분석** | 추론 시간 이벤트 | 모니터링 서비스가 구독하여 **AAR **(After Action Report) 계산 |
| **RAG 데이터 업데이트** | 사내 문서 수정 | 인덱싱 서비스가 구독하여 **벡터 DB 에 즉시 반영** |
| **보안 이상 감지** | 입력 가드레일 위반 | 보안 알림 서비스가 구독하여 **관리자에게 즉시 통보** |

## 4. EDA 도입 시 고려해야 할 인프라 리스크

### 최종 일관성 (Eventual Consistency)

> 데이터가 모든 서비스에 **즉시 동기화되지 않을 수 있습니다**.

| 주의 사항 | 설명 |
|----------|------|
| **데이터 정합성** | 실시간 정합성이 중요한 금융 결제 등에서는 주의 필요 |
| **일시적 불일치** | 짧은 시간 동안 서비스 간 데이터 불일치 발생 가능 |

---

### 운영 복잡도

| 문제 | 설명 |
|------|------|
| **클러스터 관리** | 메시지 브로커 (Kafka 등) 의 클러스터 관리 비용 증가 |
| **모니터링** | 브로커 상태, 메시지 지연 (Lag), 처리량 모니터링 필요 |

---

### 추적의 어려움

> 요청이 **비동기로 흐르기 때문에**, **분산 트레이싱 도구 **(Jaeger 등)입니다.

| 대응책 | 설명 |
|--------|------|
| **분산 트레이싱** | Jaeger, Zipkin 등 도구 도입 필수 |
| **상관 ID** | 이벤트 간 상관 관계 추적을 위한 Correlation ID 활용 |

## 💡 엔지니어링 제언: PDCA 기반의 EDA 구축

EDA 는 **구축보다 운영이 더 중요**합니다.

### Plan

> **감사 로그와 성능 분석**처럼 비동기 처리가 유리한 구간부터 **작게 시작**하세요.

### Do

> 메시지 유실 방지를 위해 브로커의 **복제 **(Replication)를 인프라 수준에서 강화하세요.

### Check

> 이벤트 처리 **지연 **(Lag)을 실시간으로 모니터링하여 병목 구간을 찾으세요.

### Act

> 장애 발생 시 저장된 이벤트를 **재처리 **(Replay)하여 데이터 유실 없이 시스템을 복구하는 훈련을 수행하세요.

## 📊 EDA vs 전통 아키텍처 비교

| 특성 | 전통 아키텍처 | EDA |
|------|-------------|-----|
| **결합도** | 강한 결합 (Tight) | 느슨한 결합 (Loose) |
| **응답성** | 동기 블로킹 | 비동기 논블로킹 |
| **장애 격리** | 어려움 | 용이 |
| **확장성** | 제한적 | 수평적 확장 용이 |
| **감사 로그** | 사후 수집 | 이벤트 기반 자동 수집 |
| **복잡도** | 낮음 | 높음 |

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 EDA 도입 검토 시 고려사항:

1. **이벤트 불변성**: 감사 로그용 이벤트의 위변조 방지와 영구 보존 메커니즘
2. **최종 일관성 관리**: 데이터 정합성 요구사항과 Eventual Consistency 허용 범위
3. **메시지 브로커 운영**: Kafka 등 브로커 클러스터의 가용성과 재해복구 계획
4. **분산 트레이싱**: 비동기 이벤트 흐름의 종단 간 추적성과 장애 원인 분석
5. **이벤트 스키마 관리**: 이벤트 형식 버전 관리와 하위 호환성 정책
6. **재처리 **(Replay): 장애 시 이벤트 재처리를 통한 데이터 복구 절차

---
