# MSA 의 3 대 핵심 원칙

모놀리스의 한계를 극복하고 엔지니어님께서 설계하신 **Compound AI System**이나 엔터프라이즈 인프라를 견고하게 운영하기 위한 **MSA 의 3 대 핵심 원칙**을 정리해 드립니다.

이 원칙들은 단순히 기술적인 분리를 넘어, **시스템의 생존성과 비즈니스 민첩성**을 결정짓는 설계의 기둥입니다.

---

## 1. 독립 배포 (Independent Deployability)

각 서비스가 **다른 서비스에 영향을 주지 않고 개별적으로 업데이트 및 출시**될 수 있어야 한다는 원칙입니다.

### 상세 설계

> 서비스 간의 결합도를 낮추기 위해 **API 기반 통신**과 **데이터베이스 분리 **(Database per Service)가 필수적입니다.

### AI 적용 시

| 상황 | 모놀리스 | MSA |
|------|---------|-----|
| RAG 파이프라인 '검색 로직' 수정 | 전체 AI Gateway 재시작 필요 | 해당 모듈만 즉시 배포 |

### 장점

> **배포 주기가 짧아져** 시장 변화나 기술 업데이트 (예: 새로운 모델 출시) 에 **즉각적으로 대응**할 수 있습니다.

---

## 2. 장애 격리 (Fault Isolation / Blast Radius Control)

특정 서비스에서 발생한 문제가 **전체 시스템으로 전파되는 것을 차단**하는 '격벽 (Bulkhead)' 원칙입니다.

### 상세 설계

> **서킷 브레이커 **(Circuit Breaker)와 **비동기 이벤트 통신**을 활용합니다.
>
> 특정 서비스가 응답하지 않으면 즉시 차단하고, 미리 준비된 **폴백 **(Fallback)을 실행합니다.

### AI 적용 시

```
특정 LLM 공급사 API 장애
        ↓
'모델 추론 서비스' 지연
        ↓
┌─────────────────────────────────┐
│  서킷 브레이커 작동             │
│  (즉시 차단 + 폴백 실행)        │
└─────────────────────────────────┘
        ↓
'가드레일'과 '사용자 UI 서비스'는 정상 작동
        ↓
사용자에게 점진적 성능 저하 (Graceful Degradation) 메시지 전달
```

### 장점

> **시스템 전체의 가용성 **(Availability)하며, 보안 침해 사고 발생 시에도 **피해 범위를 특정 서비스로 한정**할 수 있습니다.

---

## 3. 독립 스케일링 (Independent Scaling)

**서비스별로 필요한 자원의 특성에 맞춰 개별적으로 인프라를 확장**하는 원칙입니다.

### 상세 설계

> **CPU 집약적, 메모리 집약적, 혹은 GPU 집약적인 서비스**인지에 따라 인스턴스 타입을 다르게 설정하고 **오토스케일링 **(Auto-scaling)을 개별 적용합니다.

### AI 적용 시

| 서비스 | 자원 특성 | 확장 전략 |
|--------|----------|----------|
| **임베딩 서비스** | GPU 집약적 | 문서 인덱싱 시 GPU 자원 집중 할당 |
| **의도 분류기** | CPU 경량 | 가벼운 트래픽에는 소량 CPU 자원만 유지 |
| **벡터 DB** | I/O 집약적 | 대규모 조회 시 I/O 성능 높은 인스턴스로 확장 |

### 장점

> **불필요한 자원 낭비를 막아 클라우드 비용을 최적화 **(Cost Optimization)합니다.

## 💡 인프라 엔지니어를 위한 종합 인사이트

이 3 대 원칙이 지켜질 때 비로소 아키텍처는 **유연함**을 얻게 됩니다.

특히 **Samsung Austin Semiconductor **(SAS)와 같은 고가용성 인프라 환경에서는 **'장애 격리'가 보안 정책만큼이나 중요**하게 다뤄질 것입니다.

### ✅ Checklist

| 질문 | 예/아니오 | 판단 |
|------|----------|------|
| 서비스 A 를 배포할 때 서비스 B 를 함께 빌드해야 하는가? | 예 | ❌ 독립 배포 위반 |
| 데이터베이스를 여러 서비스가 공유하고 있는가? | 예 | ❌ 장애 전파 및 독립 스케일링 저해 |
| 모든 서비스가 동일한 사양의 인스턴스에서 돌아가는가? | 예 | ❌ 스케일링 비효율 발생 |

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 MSA 핵심 원칙 검토 시 고려사항:

1. **배포 독립성**: 서비스별 배포 파이프라인 분리와 변경 관리 프로세스
2. **데이터 소유권**: Database per Service 구현과 데이터 일관성 보장 메커니즘
3. **장애 격리 수준**: 서킷 브레이커, 벌크헤드, 폴백 메커니즘 구현 현황
4. **스케일링 효율성**: 서비스별 오토스케일링 규칙과 비용 최적화 효과
5. **결합도 측정**: 서비스 간 의존성과 API 계약 관리 적절성
6. **AAR 운영**: 3 대 원칙 준수 여부 지속적 점검과 개선 사이클
