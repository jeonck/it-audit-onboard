# AI 아키텍처 선택 의사결정 트리 (Decision Tree)

AI 아키텍처 설계 시 **비용 (Cost)**과 **품질 (Quality)** 사이의 균형을 잡는 것은 가장 어려운 과제입니다.

앞서 논의한 비용 최적화 원리와 품질 보장 전략을 결합하여, 실제 프로젝트에서 어떤 아키텍처를 선택해야 할지 결정하는 **의사결정 트리 (Decision Tree)**를 정리해 드립니다.

이 가이드는 **IT Security 및 Infrastructure 엔지니어링 관점**에서 시스템의 견고함과 효율성을 동시에 고려할 수 있도록 설계되었습니다.

---

## 🌳 AI 아키텍처 선택 의사결정 트리

### Step 1: 작업의 복잡도 및 요구 성능 판단

가장 먼저 해결하려는 태스크가 LLM 의 고차원적 추론을 필요로 하는지 확인합니다.

#### 단순 패턴 매칭/분류/추출인가?

| | |
|---|---|
| **Yes** | **경량 모델 (SLM) + 프롬프트 최적화**<br>결정: GPT-4o mini, Llama 3 8B 수준의 모델을 배치 처리로 운영 |
| **No** | Step 2 로 이동 |

#### 논리적 추론이나 다단계 작업 (Multi-step) 이 필요한가?

| | |
|---|---|
| **Yes** | **고성능 모델 (LLM) + Agentic Workflow** |
| **No** | 일반적인 RAG 아키텍처 검토 |

---

### Step 2: 데이터 최신성 및 신뢰성 요구사항

모델이 학습하지 않은 최신 데이터나 보안이 중요한 내부 데이터를 다루어야 하는지 결정합니다.

#### 내부 문서나 실시간 데이터 기반의 답변이 필수인가?

| | |
|---|---|
| **Yes** | **RAG(검색 증강 생성) 아키텍처**<br>세부 결정: 데이터 간 관계가 복잡하면 **GraphRAG**, 단순 검색이면 **Vector RAG** |
| **No** | Step 3 으로 이동 |

#### 환각 (Hallucination) 허용 범위가 제로 (0) 에 가까운가?

| | |
|---|---|
| **Yes** | **검증 루프 (Validation Loop) + 구조화 출력 강제**<br>결정: 출력 결과를 Pydantic 으로 파싱하고 LLM-as-a-Judge 로 사후 검증 |

---

### Step 3: 비용 및 트래픽 효율성 고려

예산 내에서 실시간 응답 속도를 확보할 수 있는지 검토합니다.

#### 동일한 유형의 질문이 반복적으로 발생하는가?

| | |
|---|---|
| **Yes** | **시맨틱 캐싱 (Semantic Caching) 도입** |
| **No** | 실시간 호출 최적화 |

#### 실시간 응답 (Latency) 이 크리티컬한가?

| | |
|---|---|
| **Yes** | **모델 계층화 (Cascading)**<br>결정: Router 를 통해 쉬운 질문은 소형 모델로 처리하여 비용과 속도 모두 확보 |
| **No** | **배치 처리 (Batch API)**. 비용 50% 절감 모드 선택 |

## 🛠 아키텍처 선택 매트릭스 (Quick Guide)

| 우선순위 | 권장 아키텍처 조합 | 주요 설계 기법 |
|----------|------------------|---------------|
| **비용 극단적 최적화** | SLM + Caching + Batch | Prompt Caching, 1-shot learning |
| **품질/신뢰성 최우선** | High-end LLM + RAG + Judge | Grounding, Self-Correction Loop |
| **개발 속도/유연성** | Serverless LLM + LangChain | Function Calling, Tool Use |
| **엔터프라이즈 보안** | On-prem/Private LLM + Guardrails | PII Masking, Local Vector DB |

## 💡 엔지니어를 위한 제언: PDCA 기반 적용

아키텍처를 선택한 후에는 **AAR(After Action Report)**을 통해 다음 지표를 주기적으로 점검하는 것이 중요합니다.

### Cost per Query

> 예상 토큰 소모량 대비 실제 비용이 적절한가? (**출력 토큰 비중 확인**)

### Faithfulness Score

> RAG 시스템이 원본 문서에 얼마나 충실하게 답변하는가?

### Latency Budget

> 유저가 체감하는 응답 속도가 서비스 수준 협약 (SLA) 을 충족하는가?

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 AI 아키텍처 선택 의사결정 시 고려사항:

1. **의사결정 근거 문서화**: 아키텍처 선택의 이유와 트레이드오프 분석 기록 확인
2. **비용 -품질 균형 검증**: 선택된 아키텍처의 Cost per Query 와 품질 지표 (Faithfulness 등) 적절성
3. **확장성 검토**: 트래픽 증가 시 아키텍처의 수평 확장 (Scaling) 가능성
4. **보안 준수**: 데이터 민감도에 따른 RAG, On-prem, Guardrails 적용 적절성
5. **SLA 이행 능력**: Latency Budget 과 실제 응답 시간 측정 및 비교
6. **지속적 개선 사이클**: AAR 기반 PDCA 운영과 지표 모니터링 프로세스 수립
