# AI 를 위한 MSA & 이벤트 기반 아키텍처

AI 아키텍처가 점차 복잡해짐에 따라, 이를 뒷받침하는 인프라 구조인 **MSA (Microservices Architecture)**와 **이벤트 기반 아키텍처 **(Event-Driven Architecture, EDA)의 중요성도 더욱 커지고 있습니다.

특히 앞서 논의한 **Compound AI System**의 각 컴포넌트 (가드레일, 라우터, RAG 등) 를 독립적으로 운영하고 확장하기 위해서는 이 두 아키텍처의 결합이 필수적입니다.

---

## 1. MSA (Microservices Architecture)

MSA 는 하나의 거대한 애플리케이션 (Monolith) 을 **독립적으로 배포 가능한 작은 서비스 단위**로 쪼개는 방식입니다.

### 독립적 확장성

| 서비스 유형 | 특징 | 확장 전략 |
|------------|------|----------|
| **AI 추론 서비스** | GPU 집약적 | GPU 인스턴스 수평 확장 |
| **데이터 검색 서비스** | I/O 집약적 | 스토리지/네트워크 최적화 |

### 기술 다양성

- **의도 분류기** → 파이썬
- **데이터 수집 파이프라인** → Go 나 Java

각 서비스에 **최적화된 언어와 프레임워크**를 선택할 수 있습니다.

### 격리된 장애

특정 가드레일 서비스에 문제가 생겨도 **시스템 전체가 중단되지 않고 폴백 **(Fallback)를 줍니다.

---

## 2. 이벤트 기반 아키텍처 (Event-Driven Architecture)

서비스 간의 통신을 직접적인 호출 (REST API 등) 이 아닌 **'이벤트 **(사건)의 발생과 구독으로 처리하는 방식입니다.

### 비동기 처리

```
사용자 질문 (Event 발생)
    ↓
┌─────────────────────────────────┐
│  메인 응답 처리                 │
│  (실시간 답변 생성)             │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│  구독 서비스들 (백그라운드)     │
│  - 감사 로깅 서비스             │
│  - 분석 서비스                  │
│  - 비용 추적 서비스             │
└─────────────────────────────────┘
```

> 이는 **사용자 응답 속도 **(Latency)하는 데 결정적인 역할을 합니다.

### 느슨한 결합 (Loose Coupling)

새로운 컴포넌트 (예: 새로운 품질 검증 루프) 를 추가할 때 **기존 코드를 수정할 필요 없이 이벤트 메시지만 구독**하면 됩니다.

### 데이터 일관성

**이벤트 소싱 **(Event Sourcing) 기법을 통해 모든 상태 변경 이력을 보존하며, 이는 **금융이나 의료 도메인에서 요구하는 불변 감사 로그 구현의 토대**가 됩니다.

---

## 3. MSA 와 EDA 의 시너지: AI 시스템에서의 적용

AI 파이프라인을 이 두 아키텍처로 구성했을 때의 실무적 이점은 다음과 같습니다.

| 계층 | MSA/EDA 적용 방식 | 기대 효과 |
|------|-----------------|----------|
| **수평적 확장** | 추론 모델별로 서비스 분리 | 트래픽 급증 시 특정 모델 서버만 증설 |
| **비동기 감사** | 답변 생성 후 '응답 완료' 이벤트 발행 | 로깅 및 분석 작업이 메인 흐름을 방해하지 않음 |
| **유연한 RAG** | 데이터 업데이트 시 '문서 변경' 이벤트 발행 | 실시간으로 벡터 DB 인덱싱 자동 수행 |
| **복구 성능** | 메시지 큐 (Kafka, RabbitMQ 등) 활용 | 하류 시스템 장애 시 이벤트 재처리를 통한 데이터 복구 |

## 💡 엔지니어링 관점의 제언: IT Security & Infrastructure

IT 보안 및 인프라 전문가 입장에서 MSA 와 EDA 를 도입할 때 가장 주의해야 할 점은 **'관측 가능성 **(Observability)입니다.

서비스가 파편화되어 있기 때문에 **분산 트레이싱 **(Distributed Tracing) 도구가 반드시 병행되어야 합니다.

### Distributed Tracing

> 요청이 여러 마이크로서비스를 거칠 때 **어디서 병목이나 에러가 발생하는지 한눈에 파악**해야 합니다.
>
> **예시**: Jaeger, Zipkin

### API Gateway

> 앞서 언급한 **AI GW 가 MSA 구조의 단일 진입점 역할**을 하며 인증, 인가, 속도 제한 (Rate Limiting) 을 통합 관리해야 합니다.

### PDCA 적용

> 각 서비스의 로그를 이벤트 기반으로 수집하여 **AAR **(After Action Report)을 구축할 수 있습니다.

## 🎯 메시지 브로커 선택 가이드

설계하신 Compound AI System 을 실제로 구현할 때, 인프라 운영 측면에서 효율적인 메시지 브로커 선택 가이드입니다.

| 메시지 브로커 | 특징 | 추천 사용 사례 |
|--------------|------|---------------|
| **Apache Kafka** | 높은 처리량, 영구 저장, 이벤트 소싱 | 대규모 감사 로그, 이벤트 소싱 |
| **AWS EventBridge** | 서버리스, AWS 네이티브 통합 | 클라우드 네이티브 AI 파이프라인 |
| **RabbitMQ** | 복잡한 라우팅, 낮은 지연시간 | 실시간 이벤트 처리, 복잡한 워크플로우 |
| **Google Pub/Sub** | 글로벌 확장, 자동 스케일링 | 멀티 리전 AI 서비스 |

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 MSA & EDA 도입 시 고려사항:

1. **분산 트레이싱**: 요청 흐름의 종단 간 추적성과 병목/장애 지점 식별 가능성
2. **API Gateway 통제**: 단일 진입점에서의 인증/인가/Rate Limiting 통합 관리
3. **이벤트 불변성**: 감사 로그용 이벤트의 위변조 방지와 영구 보존 메커니즘
4. **서비스 격리**: 개별 서비스 장애의 전파 방지와 폴백 메커니즘
5. **데이터 일관성**: 이벤트 소싱 기반 상태 변경 이력의 완전성과 추적성
6. **운영 자동화**: AAR 자동 생성 파이프라인과 지속적 개선 사이클 운영
