# MCP (Model Context Protocol) 기초 가이드

**Model Context Protocol (MCP)**는 2024 년 11 월 Anthropic 이 발표한 **오픈 표준**으로, AI 모델 (LLM) 이 외부 데이터 소스 및 도구와 통신하는 방식을 표준화하기 위해 탄생했습니다.

IT 인프라 전문가이신 엔지니어님께 익숙한 비유를 들자면, MCP 는 AI 시스템을 위한 **"USB-C 포트"**와 같습니다. 주변기기마다 전용 케이블을 만들던 시대를 끝내고, 하나의 표준 포트로 모든 장치를 연결하는 아키텍처를 지향합니다.

---

## 1. 탄생 배경 및 해결하는 문제 (N × M 통합)

과거 AI 에이전트를 구축할 때 가장 큰 병목은 **N 개의 AI 모델을 M 개의 도구/데이터에 연결하는 방식이 파편화**되어 있다는 점이었습니다.

### 기존의 문제 (N × M)

> 새로운 모델 (GPT, Claude, Gemini 등) 이 나올 때마다 **각기 다른 방식의 도구 호출 **(Function Calling)를 맞춰야 했고, 새로운 데이터 소스 (Slack, GitHub, DB 등) 를 추가할 때마다 **각 모델에 맞춘 커스텀 연동 코드를 새로 작성**해야 했습니다.

이는 유지보수 비용을 **기하급수적으로 증가**시켰습니다.

```
┌─────────────────────────────────────────────────────────┐
│  기존의 문제 (N × M) - 파편화된 통합                    │
├─────────────────────────────────────────────────────────┤
│  GPT-4 ──→ Slack 연동 (별도 구현)                      │
│  GPT-4 ──→ GitHub 연동 (별도 구현)                     │
│  Claude ─→ Slack 연동 (별도 구현)                      │
│  Claude ─→ GitHub 연동 (별도 구현)                     │
│  Gemini ─→ Slack 연동 (별도 구현)                      │
│  Gemini ─→ GitHub 연동 (별도 구현)                     │
│                                                         │
│  → 3 모델 × 2 도구 = 6 개의 별도 연동 코드 필요        │
│  → N 모델 × M 도구 = N × M 개의 연동 코드              │
└─────────────────────────────────────────────────────────┘
```

---

### 해결 방식 (N + M)

> **MCP 라는 표준 인터페이스를 중간에 둠**으로써, 모델은 **MCP Client 표준만 준수**하면 되고, 데이터 소스는 **MCP Server 규격에 맞춰 한 번만 개발**하면 됩니다.

결과적으로 복잡도가 **곱셈 **(N × M)으로 줄어들며 생태계 통합이 가능해졌습니다.

```
┌─────────────────────────────────────────────────────────┐
│  MCP 해결 방식 (N + M) - 표준화된 통합                  │
├─────────────────────────────────────────────────────────┤
│  [AI Models]        [MCP]        [Data/Tools]          │
│  GPT-4 ──┐                                              │
│  Claude ─┼──→ MCP Client ←──→ MCP Server ←── Slack     │
│  Gemini ─┘         │              │                     │
│                    │              └── GitHub            │
│                    │              │                     │
│                    │              └── DB                │
│                                                         │
│  → 3 모델 + 2 도구 = 5 개의 표준 연동만 필요           │
│  → N 모델 + M 도구 = N + M 개의 표준 연동              │
└─────────────────────────────────────────────────────────┘
```

## 2. 아키텍처 (Host, Client, Server)

MCP 는 크게 **세 가지 계층**으로 구성된 클라이언트 - 서버 구조를 따릅니다.

### MCP Host

> **사용자가 직접 사용하는 최상위 어플리케이션**입니다.

| 예시 | 설명 |
|------|------|
| **Claude Desktop** | Anthropic 공식 데스크톱 앱 |
| **Cursor** | AI 기반 코드 에디터 |
| **IDE** | JetBrains, VS Code 등 |

모델 실행 환경을 관리합니다.

---

### MCP Client

> **Host 내부에 존재하며 Server 와 실제로 통신하는 통로**입니다.

모델의 요청을 서버 규격으로 변환하고 서버의 응답을 모델에 전달합니다.

---

### MCP Server

> **실제 데이터나 도구의 실행 권한을 가진 경량 서비스**입니다.

로컬 파일 시스템, DB, 외부 API 등을 추상화하여 Client 에 노출합니다.

```
┌─────────────────────────────────────────────────────────┐
│  MCP 아키텍처                                            │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────┐                                        │
│  │  MCP Host   │  (Claude Desktop, Cursor, IDE)        │
│  │  ┌───────┐  │                                        │
│  │  │ MCP   │  │                                        │
│  │  │Client │  │                                        │
│  │  └───┬───┘  │                                        │
│  └──────┼──────┘                                        │
│         │ MCP Protocol (JSON-RPC 2.0)                  │
│         │                                               │
│  ┌──────┴──────┐                                        │
│  │  MCP Server │  (경량 서비스)                        │
│  │  ┌───────┐  │                                        │
│  │  │Resources│  → 파일, DB 레코드, API 캐시          │
│  │  ├───────┤  │                                        │
│  │  │ Tools │  → GitHub 이슈 생성, 코드 실행          │
│  │  ├───────┤  │                                        │
│  │  │Prompts│  → 코드 리뷰, 데이터 분석 템플릿       │
│  │  └───────┘  │                                        │
│  └──────┬──────┘                                        │
│         │                                               │
│  ┌──────┴──────┐                                        │
│  │ 실제 시스템  │  (파일시스템, DB, 외부 API)           │
│  └─────────────┘                                        │
└─────────────────────────────────────────────────────────┘
```

## 3. 핵심 Primitive (빌딩 블록)

서버가 클라이언트 (모델) 에게 제공하는 **세 가지 핵심 자원**입니다.

### Resources (자원)

> AI 가 **읽을 수 있는 데이터 엔티티**입니다.

| 예시 | 특성 |
|------|------|
| 파일 내용 | 읽기 전용 컨텍스트 |
| DB 레코드 | 읽기 전용 컨텍스트 |
| API 캐시 | 읽기 전용 컨텍스트 |

---

### Tools (도구)

> AI 가 **실행할 수 있는 함수/액션**입니다.

| 예시 | 특성 |
|------|------|
| GitHub 이슈 생성 | 부수 효과 (Side Effect) 발생 |
| 코드 실행 | 부수 효과 발생 |
| DB 쓰기 연산 | 부수 효과 발생 |

---

### Prompts (프롬프트)

> AI 의 행동을 **가이드하는 사전 정의된 템플릿**입니다.

| 예시 | 설명 |
|------|------|
| 코드 리뷰 | 특정 작업을 위해 최적화된 지시문 세트 |
| 데이터 분석 | 서버가 제공하는 프롬프트 템플릿 |

---

## 4. 통신 방식: JSON-RPC 2.0

MCP 의 전송 계층은 **JSON-RPC 2.0 프로토콜**을 기반으로 하며, **상태 저장 **(Stateful)을 유지합니다.

### 표준 메시지 구조

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "create_github_issue",
    "arguments": {
      "title": "Bug fix",
      "body": "Description..."
    }
  },
  "id": 1
}
```

| 필드 | 설명 |
|------|------|
| **jsonrpc** | 프로토콜 버전 (항상 "2.0") |
| **method** | 호출할 메서드 이름 |
| **params** | 메서드 파라미터 |
| **id** | 요청 식별자 (응답 매칭용) |

---

### 메시지 타입

| 타입 | 설명 | 예시 |
|------|------|------|
| **Requests** | 응답을 기대하는 요청 | `tools/call` |
| **Responses** | 요청에 대한 결과 (Success/Error) | `{"result": {...}}` |
| **Notifications** | 응답이 필요 없는 단방향 메시지 | 로그 알림 |

---

### Transport (전송 방식)

#### STDIO

> **동일 머신 내 로컬 통신** 시 표준 입출력을 활용합니다.

엔지니어님께서 로컬 MCP 서버 구축 시 주로 사용하시는 방식입니다.

```bash
# 로컬 MCP 서버 실행 예시
npx -y @modelcontextprotocol/server-filesystem /path/to/files
```

---

#### HTTP/SSE (Server-Sent Events)

> **원격 서버와 통신**할 사용하며, 서버 보낸 이벤트를 통해 비동기 응답을 처리합니다.

```
┌─────────────┐         HTTP/SSE         ┌─────────────┐
│  MCP Client │ ───────────────────────→ │  MCP Server │
│             │ ←─────────────────────── │             │
│             │    Server-Sent Events    │             │
└─────────────┘                          └─────────────┘
```

## 💡 엔지니어링 포인트: 보안과 확장성

보안 전문가 관점에서 MCP 는 **보안 경계 **(Security Boundary)가 매우 용이합니다.

### 보안 장점

| 특징 | 설명 |
|------|------|
| **명시적 노출** | Server 는 자신이 허용한 Resources 와 Tools 만 명시적으로 노출 |
| **권한 대리** | Host 와 Client 가 사용자의 권한을 대리 수행 |
| **격리된 실행** | 각 Server 는 독립된 보안 컨텍스트에서 실행 |

---

### 확장성 장점

| 특징 | 설명 |
|------|------|
| **표준 인터페이스** | 새로운 모델/도구 추가 시 표준만 준수하면 됨 |
| **동적 발견** | 실행 시점에 사용 가능한 Tools/Resources 자동 발견 |
| **플러그인 아키텍처** | Server 를 플러그인처럼 추가/제거 가능 |

---

## 📊 MCP vs 기존 통합 방식 비교

| 항목 | 기존 방식 (Function Calling) | MCP |
|------|---------------------------|-----|
| **통합 복잡도** | N × M (기하급수적) | N + M (선형적) |
| **표준화** | 벤더별 상이 (OpenAI, Anthropic 등) | 오픈 표준 (Anthropic 주도) |
| **도구 발견** | 수동 등록 필요 | 동적 발견 (Discovery) |
| **확장성** | 코드 수정 필요 | Server 추가만 |
| **보안 경계** | 모델별 상이 | 일관된 Security Boundary |
| **유지보수** | 복잡도 높음 | 복잡도 낮음 |

---

## 감리 관점에서의 시사점

정보시스템 감리 관점에서 MCP 도입 검토 시 고려사항:

1. **표준 성숙도**: 2024 년 11 월 발표된 비교적 새로운 표준 (지속적 모니터링 필요)
2. **보안 경계**: Server 별 명시적 노출과 권한 관리 적절성
3. **감사 추적성**: JSON-RPC 메시지의 무결성과 로그 보존
4. **상호운용성**: 벤더 중립적 표준으로 락인 (Lock-in) 위험 최소화
5. **확장성**: N+M 복잡도로 인한 유지보수 비용 절감 효과
6. **동적 발견 리스크**: 자동 도구 발견의 보안 검증 메커니즘
